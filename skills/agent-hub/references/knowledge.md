# 长期知识的提炼与审核

适用于服务端 0.12.0 / 迁移 0015、桌面端 0.14.0。日志交接记录进展；长期知识保存会继续影响后续开发的接口约定、决定、约束、经验和错误预防。原文、候选和全部处理决定均保留。

## 何时提炼

每轮先完成原有工作日志。仅在长期事实新增或变化时提炼，通常最多 3 条；普通进度、未经验证的推测和重复结论继续放日志，不重复生成卡片。提炼由当前获准的本地 Agent 或人员进行，服务器不会自行启动模型。

1. 用 `hub_search_knowledge` 检索相关主题，核对当前适用结论。追溯时使用 `include_history: true`，候选、冲突和旧版本不得当作当前事实。
2. 从 `hub_search_memory` 取得来源卡片及 `source_hash`，必要时用 `hub_read_memory_source` 展开原文。同任务旧日志可以在历史范围读取并沉淀长期事实，新进展不会自动否定其中全部有效约定。
3. `hub_propose_knowledge` 每次提交一条候选：`source_card_id`、`source_hash`、逐字出现在来源卡片中的 `source_quote`，以及稳定 `topic`、`kind`、标题、长期结论和提炼原因。例如主题 `web.auth.device-approval`，类型为 constraint、decision、interface、lesson 或 pitfall。
4. 一条候选只绑定一个来源，分别整理不同原文支持的结论，不拼接其他仓库或不可读资料。固定仓库连接自动限定范围。引用能追溯来源，不证明模型推论正确。
5. `generation` 可记录本地工具、作者报告的模型、提示版本及 Token 用量；这些值不是已验证的模型身份或服务商账单。不要填模型凭证、私钥或完整调用请求。

写入使用稳定 `operation_id`；网络重试保持同一 ID 和内容。提交候选不表示已经审核或进入开工记忆。

## 审核与替换

`hub_decide_knowledge` 需要 tasks:publish 和当前来源读取权，传入 `fact_id`、`expected_version`、处理状态及原因。通常由其他人批准；超管本人批准自己的候选必须明确记录 `override_reason`，不能称为独立审核。

同一项目、仓库资料范围和 `topic` 只允许一个生效结论。替换时核对旧结论，再传 `replaces_id`、`replaces_version`；服务器原子替换，保留双方及审核记录。已有结论不可读时联系获权负责人，不能更换主题绕过冲突。

可以标记 conflicted、retired 或 rejected。新内容须提交新候选，不能覆盖旧正文。主题冲突检测依赖明确相同标识，不代表自动识别任意文字的语义矛盾。

## 开工与失效

`hub_prepare_work` 自动把匹配且经审核的有效知识放入 `payload.memory.knowledge`，与交接摘录共用 12,000 UTF-8 字节预算。阅读来源、版本和缺口，按需展开，不加载全部历史。

新日志只替代任务交接，不会自动删除已审核的长期知识。原始卡片冲突或退役、文档换版或删除、文档源配置改变时，相关知识退出默认结果；处理自动留痕。未改变内容的文档重复同步保持结论有效。

来源撤权立即关闭知识及旧准备包读取。已加载结论退役、替换或失效时，修改检查及受管提交要求重新准备；恢复来源不会自动重新批准旧知识。知识是项目资料，实际权限、任务范围和禁改路径以当前正式规则为准。

PC“共享记忆”可切换长期知识及候选历史。Web“共享记忆”提供候选提交、审核、冲突处理和显式替换。语义向量召回、自动跨原文综合和长期规模效果评测仍待完成。
