# 审计整改与复评

> 2026-11-07。范围：当前身份/项目后台和 Windows 桌面客户端的四项已确认问题；完整协作框架的实施边界仍以[生产实施基线](14_跨端协作Skill框架_生产实施基线.md)为准。发布状态以本文“部署证据”节的最终核验为准。

## 一、整改结论

本轮将并发、更新清单、登录限流与设备审批四项问题落到代码和回归测试。服务器独立 `hub_test` 的 **67 项测试通过**，本机 Windows 的 **29 项桌面测试通过**，后端 Ruff 检查通过。数据库、Docker 和数据库测试均在指定 `47.109.23.86`，本机没有安装或启动数据库/Docker。

这些结果支持发布当前基础服务的补丁，不能作为完整跨端协作平台的生产验收。项目组多仓库授权、任务原子认领、逐轮快照交接和撤权上传卸载仍缺运行实现。

## 二、已整改的四项问题

| 原问题 | 修改 | 本轮证据 |
|---|---|---|
| 全局数据库锁把所有 API 串行化，SMTP 持锁；业务事务内的安全事务共用池可能互相等待 | 普通事务按人员/资源及项目排序协调，读操作共享；恢复操作保留全局屏障。安全辅助操作分池，连接和 SQL 等待有上限。加密投递意图先提交，离开事务再发 SMTP | 慢 SMTP 时业务池检出连接为 0，同一超管仍能查询；仅两个业务连接的并发写入均成功；不同项目可继续查询；撤权与已执行写入按锁顺序完成，撤权后拒绝访问；并发刷新触发重放家族吊销 |
| 合法旧更新清单可无限回放，冻结客户端版本 | 签名内加入递增 `metadata_version`、签发时间和最长 31 天有效期。客户端保存已见编号与检查时间，拒绝到期/回退/编号复用/明显时钟回退。无有效联网清单时暂停普通项目操作 | 清单过期、未来签发、非法时间、超长有效期、回放、重启保留编号、同编号替换和离线测试通过；历史已安装包在其清单过期后仍能启动 |
| 任意登录名先建限流桶，拒绝流量也能制造持久记录；桶无清理 | IP 限流和设备证明先执行，只有真实账号才建立账号桶；过期桶每次限量清理 100 条，计数饱和到 limit+1。未认证的入口限流/缺证明错误不逐条写审计；入口 Nginx 增加登录和初始化限流 | 随机账号和缺证明请求不增加账号桶；IP 拒绝后桶数量不增、计数封顶；250 个过期桶分批清理到 150、50 |
| 设备审批过期后不能重申，列表前 100 条过期申请堵住新申请 | 原设备重新登录可产生新申请并保留旧历史；重复登录复用有效申请；明确拒绝不能自动重申；列表过滤已过期记录并分页；审批过期时持久标记 expired | 设备 ID 保持、新申请唯一、拒绝不复活；105 条过期和 105 条有效申请分页后只返回 105 条有效记录；过期决策写入 expired |

并发增加后补上 Argon2 并发上限：当前单进程 API 最多同时两次密码哈希/验证，避免 512 MiB 容器在登录突发时被内存耗尽。扩大 API 进程数/副本数时，需重新计算密码内存、数据库连接和入口限额。

### 邮件故障处理

邮件 outbox 复用现有表，没有新数据库。收件人和验证码通过与 SMTP 设置不同用途的派生密钥加密；投递结束后清除正文。请求返回前仍等待投递结果，但 SMTP 期间不占业务连接和协调锁。

API 中断后由后台恢复投递，运行租约 3 分钟，最多领取 3 次。明确发送失败时清理未消费的挑战，允许重新请求，邮件限额不会回滚。已消费挑战不会被晚到的错误回调删除。回归覆盖重复领取、过期取消、投递中断恢复、失败重发及投递期间已完成验证码验证的情况。

SMTP 无法保证恰好投递一次；服务在收到 SMTP 接受响应后、记录结果前崩溃时，可能重复收到同一验证码。不能从“请求异常”推断“收件人一定没收到”。

## 三、更新发布与运维约束

- 后端补丁版本 `0.3.1`，增量迁移 `0006`；桌面 `0.3.2`。版本号分别维护，含义不同。
- 保持清单 schema 1，旧桌面 `0.3.1` 能校验新清单并升级；旧客户端本身尚无新鲜度保护，需实际升级。
- 默认签发 30 天。相同 ZIP 可续签更高清单编号，不能重打包复用已发布的软件版本。发布机必须保留最高编号；更换发布机先保存正式清单。
- 每 14 天由发布操作人续签；到期前至少 72 小时处理。续签命令和只读核验脚本见[桌面说明](../projects/agent-hub-desktop/README.md#清单续签与失效处理032)。
- 增加服务端 `agent-hub check-desktop-feed` 及每 6 小时的 systemd 检查。剩余不足 72 小时返回 2，失效/网络/签名异常返回 1；结果进入 systemd journal。该检查不持有私钥，不自动续签，不发送外部消息；持续告警的接收人和处理责任仍需运维落实。
- 清单失效暂停普通项目调用，桌面和已安装程序仍可启动，本地工作保留。未来的保全、补传和收尾入口必须保持独立，本轮没有实现这些新工具。
- 当前仍是单一内置公钥。根密钥轮换、角色分离及阈值签名尚未实现；密钥事故仍需要受控分发新信任根客户端。此实现参考了 [TUF 的有效期和回退防护原则](https://github.com/theupdateframework/specification/blob/master/tuf-spec.md)，不是完整 TUF。
- 时间校验依赖操作系统时钟；已保存的检查时间能发现明显回退，不能抵抗本机用户同时修改程序、缓存和时钟。

### 桌面

使用 Node 内置测试运行器执行 `core.test.cjs`、`reliability.test.cjs`、`update.test.cjs`：29 项通过。签名工具再次核验实际发行包的文件清单和摘要；额外用已发布的旧 0.3.1 验签模块读取新清单，确认旧客户端可迁移。

本轮没有重新验收两台物理设备、macOS 或七种 harness 的全部生命周期 Hook；这些能力不能由 Windows 单测推导。
