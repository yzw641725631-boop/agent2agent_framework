## 完整工作树备份

| 范围 | 本版容量 |
| --- | --- |
| Git 基线 | 最多 10000 文件、64 MiB、单文件 16 MiB |
| 本轮变更 | 最多 100 文件、16 MiB、单文件 4 MiB，删除也计文件数 |
| v2 清单 / 压缩容器 | 8 MiB / 96 MiB |
| 本机单条加密记录 / 总配额 | 192 MiB / 512 MiB，最多 100 条 |

小快照继续采用 v1。超过旧版基线的文件数、总量或单文件容量时使用 v2：一个 gzip 内按顺序保存标识、长度、规范 JSON 清单和原始文件体。服务端逐个验证文件，不保留整个基线的 Base64；代码审查只保留当前请求文件。Git 提交、目录树、blob、SHA256、原始变更证据、路径和凭证检查继续执行。

日志共享、代码备份、Git 交付各有独立回执。网络失败保留本机加密记录；相同清单重试返回同一回执。撤权后停止普通操作，限定上传保全通道继续核验身份与范围。获得代码读权限的接手人取回后在 PC 导出到新目录，不覆盖原工程，不恢复 Git 历史，也不会因此认领任务。

v2 接手人须使用 Windows 0.23.1 或更新版本。服务端数据库结构保持 0031。业务运行时回退使用另建的 0.20.0 兼容镜像，明确带入 v2 解码、加密存储和单文件审查适配，不改动已发布的 0.20.0 目录。

## 长期记忆基准

固定 24 个合成问题，覆盖旧但仍有效的规则、明确替代、冲突和停用、跨仓库与来源撤权、索引落后、改写问法、长条目预算、读额度耗尽和增量已读。

实际调用原生 PostgreSQL 授权查询、关键词排序、pgvector 精确距离、RRF 混合检索，以及开工包和增量经验。不会把夹具提供的排序当作原生检索结果。文档下载源使用合成接口，向量来自固定的真实 CPU 模型；相同的噪声正文复用相同的真实向量，减少基准建库成本。检索和 RLS 均实际执行。

历史噪声分 64、512、2048 条三档递增。报告记录完整响应的 `cl100k_base` 参考 Token、SQL 与向量请求数、延迟、漏召回、旧/冲突内容暴露、未授权内容暴露、预算和重复读取成本。

测量的是模型能否从交付上下文取得所需事实，未调用完成模型生成答案，不能视为答案正确率。人工合成候选的提炼输入/输出只计参考 Token；真实提供方用量、账单和在线 Hindsight 对照尚未测量。完整原始分项、SQL/编码请求与重复读取指标见[原生基准数据](审计数据/2026-11-11_0231_原生记忆基准.json)。

全部策略、全部档位越权暴露均为0。分层在三档中均支持18/19个事实；唯一缺失是故意超过1024参考Token预算的长条目，预算门禁按预期拒绝装入。全量保留了原始历史，六处失效或冲突内容仍会暴露。

在2073张卡片时，分层完整输入参考Token比全量少约77.0%；在87张卡片时，全量仅50,371，分层为187,403。这说明上下文包含的结构和来源元数据有固定开销，不能宣称所有任务都会节省Token。

同一2073卡片档的增量重复案例，首次开工包加经验召回共8,120参考Token，后续仅做经验召回，已读回执后的响应为3,694，省略8个已读条目。两次返回范围不同，不用它们直接推算同一调用的节省率。重复召回耗时4,444毫秒、执行82次SQL；缩减正文并不表示检索计算成本同比下降。

当前分层读取包含开工包和经验召回，SQL和来源/状态校验开销随历史增长，延迟偏高。本版完成可复现测量，未修改检索实现，也没有证明延迟已优化；下一步应按报告中的SQL次数、状态过滤和重复读取路径做性能治理。基准进程峰值RSS为326,586,368字节。

```sh
python scripts/run-memory-benchmark.py --output /reports/memory-quality.json
```
