# 数据模型与事务

> v0.2｜2026-11-05｜完整目标的逻辑模型；P1 身份子集已有可执行迁移，具体范围见[实施记录](06_实施记录.md)。

## 1. 建模约定

- 稳定对象 ID 使用 UUID，项目显示名、目录名、角色名称均不作为跨设备主键。
- 服务器时间使用 UTC，展示按用户时区；需要顺序保证时使用版本和代次，不依赖设备时钟。
- 项目业务表包含 `project_id`，并使用复合外键约束关联对象属于同一项目。
- 可变对象带 `version`；账号、设备、项目成员关系、grant 分别有撤销版本。
- 人员与项目撤销采用状态变更及审计记录，保留任务和制品历史。
- 敏感凭证只保存适当的密码哈希或 Token 摘要；设备表只保存公钥。

## 2. 身份、审批与授权

| 实体 | 核心字段 | 主要约束 |
|---|---|---|
| users | id, login_name, password_hash, platform_role, admin_eligible, status, auth_epoch | login_name 唯一；只有超管可授予管理员资格 |
| verified_emails | user_id, email, verified_at, active | 管理员激活必须关联有效已验证邮箱；更换邮箱重新验证 |
| devices | id, user_id, public_key, key_thumbprint, os, status, approved_by, device_epoch | 公钥指纹唯一；批准者必须是超管 |
| email_challenges | id, user_id, device_id, purpose, digest, expires_at, attempts, consumed_at | 用途、设备与邮箱绑定；有效期内单次消费；限制尝试和发送 |
| approval_requests | id, kind, requester_id, subject_user_id, payload, payload_hash, status, decided_by, version | 精确记录项目、设备、能力；只能由超管批准 |
| project_memberships | project_id, user_id, role, status, membership_epoch | UNIQUE(project_id,user_id)；项目管理员授予需超管审批 |
| access_grants | id, project_id, user_id, device_id, approval_id, capabilities, status, grant_epoch, expires_at | 不能超出获批请求；首次激活和扩权必须关联批准记录 |
| auth_sessions | id, user_id, device_id, grant_id, family_id, refresh_digest, state, expires_at | 项目访问会话绑定一个 grant；刷新轮换；不复制密码和原始刷新令牌 |
| device_control_sessions | id, device_id, approved_at, status | 只允许本人设备状态与退出恢复；不给项目正文访问权 |
| recovery_codes | user_id, code_digest, consumed_at | 超管离线恢复使用，单次消费、完整审计 |

普通成员的邮箱可以为空。将普通成员提升为管理员时，先满足邮箱条件，再由超管批准角色；不能通过移除邮箱保留有效管理员状态。

`approval_requests` 建议状态：`pending_verification → pending_approval → approved/denied/expired`。获批后签发动作记录为 `issued`，签发必须重查账号与项目当前状态。修改请求内容需要新请求或递增版本并清空旧批准。

设备状态：`pending → approved → revoked`。已批准设备删除本地密钥后重新生成密钥，应视为新设备重新验证和审批。

## 3. 项目与文档

| 实体 | 核心字段 | 主要约束 |
|---|---|---|
| projects | id, slug, name, status, created_by, version | 创建者必须是超管；slug 唯一 |
| project_repositories | id, project_id, provider_ref, canonical_branch, observed_commit | Git 凭证独立保管；不能接受客户端任意 URL 拉取 |
| document_versions | id, project_id, repo_id, doc_id, relative_path, git_commit, content_hash, title, tags, indexed_body | 同一仓库提交和路径唯一；对象引用包含 project_id |
| document_heads | project_id, doc_id, version_id | 只指向当前发布分支已接收的版本 |
| document_proposals | id, project_id, actor_id, base_hash, candidate_hash, state, git_ref | 条件编辑，冲突产生提案，不覆盖他人变更 |

数据库内的正文是检索和读取副本。Git 文档修改只有在目标提交被接收后才更新 head。需要读取分支版本时，客户端必须指定登记过的仓库和提交，权限检查保持一致。

实时任务状态不从 Markdown 的可编辑 `status` 字段反向恢复；任务状态快照由事件生成。任务说明中保留稳定任务 ID 和需求内容，执行状态由主库管理。

## 4. 任务与执行

| 实体 | 核心字段 | 主要约束 |
|---|---|---|
| tasks | id, project_id, task_key, spec_document_id, spec_revision, state, owner_attempt_id, execution_epoch, version | UNIQUE(project_id,task_key)；一个主执行实例 |
| task_dependencies | project_id, task_id, depends_on_id | 同项目复合外键；无自依赖、无环；首版不支持隐式跨项目依赖 |
| execution_runs | id, project_id, user_id, device_id, session_id, harness, state | 人、设备、harness 会话分别记录 |
| task_attempts | id, project_id, task_id, run_id, state, fence, lease_expires_at | 每个任务最多一个 active attempt |
| write_reservations | id, project_id, attempt_id, scope_key, declared_paths, expires_at | 服务端协调写范围；本地任意编辑不因此获得强制文件锁 |
| checkpoints | id, project_id, attempt_id, base_commit, head_commit, git_ref, summary, next_action, evidence_refs | 与执行代次关联；交接引用已上传制品或已推送提交 |
| submissions | id, project_id, attempt_id, fence, artifact_id, head_commit, review_state | 接收时重查当前所有者与代次；不自动合并 |

任务状态建议：`draft → ready → in_progress → review → done`，另有 `blocked`、`cancelled`。依赖是否满足、验收是否通过分别记录，不能用 Agent 自称完成代替。

关键唯一约束示意：

```sql
CREATE UNIQUE INDEX one_active_attempt_per_task
    ON task_attempts (project_id, task_id)
    WHERE state = 'active';
```

该约束不引用当前时间。租约到期后，必须在事务中先结束旧 active attempt，再创建新的；执行代次随之增加。租约到期不意味着旧进程已停止，提交入口仍需校验 fence。

## 5. 部署、上传与退出

| 实体 | 核心字段 | 主要约束 |
|---|---|---|
| deployments | id, project_id, user_id, device_id, framework_version, manifest_hash, generation, state | 清理对象绑定一个登记的部署；本机绝对路径不作跨设备主键 |
| deployment_manifest_versions | deployment_id, version, digest, signed_manifest_ref | 新安装、升级、生成框架文件需更新清单并留痕 |
| closeout_jobs | id, project_id, user_id, device_id, deployment_id, revocation_epoch, state, snapshot_receipt_id | 对同一撤销事件与部署幂等；上传与清理状态独立 |
| closeout_capabilities | id, job_id, device_key, allowed_actions, token_digest, expires_at, state | 仅绑定退出作业，无读资料、认领或普通写入能力 |
| upload_sessions | id, project_id, job_id, expected_manifest_hash, expected_bytes, state | 分块、断点和配额；不能当作普通任务提交 |
| artifacts | id, project_id, owner_id, storage_key, content_hash, size, state | storage_key 由服务端生成；验证完成前不可签发接收回执 |
| artifact_receipts | id, project_id, job_id, artifact_id, manifest_hash, durable_at, signature | 制品持久化及元数据提交后才生效 |
| cleanup_reports | id, project_id, job_id, deployment_id, plan_hash, local_result, reported_at | 区分成功、部分失败、锁定、待处理；客户端自报不等同于独立远程证明 |

平台可以证明已收到指定快照，以及客户端报告了哪些清理步骤；不承诺验证任意不受管终端上不存在其他文件副本。

## 6. 通用基础表

| 实体 | 职责 |
|---|---|
| audit_events | 记录操作者、项目、对象、动作、结果、请求 ID；不记录原始凭证和验证码 |
| outbox_events | 与业务状态同事务写入，供邮件、Git 归档、外部撤权和索引 Worker 消费 |
| idempotency_records | 以调用者、项目、动作、幂等键去重，保存请求哈希和结果引用 |
| background_jobs | 作业租约、尝试次数、重试时间和终态；处理进程崩溃后可接管 |

审计保留、制品保留和删除期限在上线前配置；索引不是审计备份。首版以数据库事件为恢复依据，Git 生成快照用于可读留痕。

## 7. 关键事务

### 7.1 授权审批与签发

锁定请求及目标账号/设备/成员关系，确认审批者为有效超管；比对请求版本和 payload_hash；确认项目和所申请能力仍有效；创建或更新 grant，写审计和 outbox 后提交。签发给客户端的凭证仅覆盖该 grant。

幂等键重复但请求内容不同时拒绝，不得重复创建扩大权限的授权。会话续期使用现有批准记录，并再次检查所有撤销版本。

### 7.2 任务认领

1. 在一个短事务中锁定并重查执行者账号、设备、成员关系和 grant。
2. 取得项目的短期协调锁，校验依赖和写范围冲突，再锁定目标任务。
3. 清算已经过期的旧 attempt；确认任务可认领。
4. 增加 execution_epoch，创建 active attempt 和写范围记录，更新 owner。
5. 写审计与 outbox，提交后返回 fence 和租约。

涉及同类多条记录时按 ID 排序锁定；总体顺序为账号、设备、成员关系、grant、项目协调锁、任务。撤销、接手、任务发布和依赖修改遵循同一协调顺序，处理死锁或序列化失败时有界重试。

指定任务认领失败返回已占用结果；可以为“领取下一项”队列使用适当的跳锁查询，但不能用跳锁把占用任务误报为不存在。

### 7.3 撤销与并发提交

撤销事务先更新对应状态和撤销版本，使旧授权不再有效，并冻结有关 attempt，创建各部署的退出作业，写审计与外部 Git 撤权事件。

正常提交与撤销锁定同一授权对象，提交还检查任务 fence。结果以事务提交顺序线性化：撤销提交后新到达的普通操作不得写入；撤销之前已提交的合法结果保留。

长上传不持有数据库长事务。完成上传时重新校验权限：普通上传若已撤权则拒绝普通提交；退出上传只能进入对应收尾作业的待审区。

### 7.4 接收回执与清理

制品字节落盘、哈希和清单验证完成后，提交 artifacts 与 artifact_receipts 的状态。客户端取得可验证回执后才进入清理；HTTP 200、上传链接生成、分块完成或数据库有一条文件记录都不能单独代替回执。

### 7.5 数据库与 Git 一致性

数据库、Git 和制品存储之间不假设分布式原子事务。使用 outbox、内容哈希、幂等事件 ID 和可见同步状态处理重试。

- 任务事件：DB 先提交，Worker 生成 Git 快照；归档未完成显示 `archive_pending`。
- 文档发布：Git 提交接收后，Worker 更新对应文档版本和索引头。
- 制品接收：先持久化字节，再提交回执；孤立临时对象按状态回收。
- 外部撤权：数据库先收回平台权限，Worker 重试 Git 成员或项目凭证撤销。

## 8. RLS 与访问检查

项目表按成员关系、账号状态和明确能力限制操作，缺少可信事务上下文时默认拒绝。复合外键阻止将 A 项目的任务绑定到 B 的文档或制品。

正常应用角色与迁移角色分离。运行角色不拥有表；需要时启用 FORCE ROW LEVEL SECURITY。超级管理员的应用身份仍通过受控策略处理，不能让客户端选择数据库超级用户连接。

退出存储使用独立、窄范围的接口或数据库函数：仅检查匹配 job、device key、deployment 和能力，不需要恢复正常项目成员资格。退出凭证不能查询普通项目表。

首版只以当前数据库状态做正向授权判定；事件用于通知和投影，不替代权威检查。
