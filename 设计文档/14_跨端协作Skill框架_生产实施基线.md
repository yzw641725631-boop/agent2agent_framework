## 1. 结论：要做的不是超级提示词，而是一个受管协作系统

产品定位：**独立发布的通用 Skill，带领不同设备上的不同 coding harness，在各自获准的工程中工作，共享获准的业务知识，并持续留下可恢复、可接手的工作状态。**

采用四个相互配合的部分：

1. **Skill：工作方法。** 保留原框架的项目组、角色、专注模式、链路、门控、知识和经验；按任务加载，不能充当鉴权系统。
2. **桌面端和本机执行组件：本机事实。** 登录、版本检查、按授权组装、事件采集、改动检测、快照、离线待传队列、配置安装和清理。
3. **Agent Hub：协作事实。** 授权、审批、任务认领、执行代次、工作记录、上下文准备、快照回执、撤权与收尾。
4. **Git + 服务器 PostgreSQL + 制品存储：可恢复数据。** Git 管正式版本；数据库管事务和记录；制品保存未提交工作；向量是可重建的检索增强。

保留现有 FastAPI、Electron、PostgreSQL 体系，不另起账号系统，不为记忆再堆一套数据库。第一步应完成“受管任务—逐轮记录—可恢复检查点”，不是先建设大规模向量索引。

这里的“强制”有明确边界：服务器可以拒绝未授权请求、重复认领和不完整交付；受管客户端可以在可用的宿主入口检查、阻止和留证。**普通用户自有电脑上的 Skill/MCP 无法保证阻止任意终端编辑、复制文件、禁用插件或删除所有历史副本。** 若业务要求抵抗恶意本机管理员，需要受控开发环境或设备管理，那是额外的部署等级。

## 3. GitHub 开源项目：借鉴机制，不整套叠加

以下为 2026-11-06 查阅上游的结果，不是本项目的集成或性能测试。采用代码前还需锁定提交、核对该提交的 LICENSE/NOTICE、依赖和安全状态；不从项目宣传直接推算本系统效果。

| 上游 | 值得借鉴 | 在本系统中的取舍 |
|---|---|---|
| [Agent Skills 规范](https://agentskills.io/specification) | `SKILL.md`、脚本、按需参考资料的通用结构 | 统一 Skill 内容；不同 harness 的安装、发现、权限和 Hook 另做适配，不认为格式兼容就代表运行语义兼容 |
| [Superpowers](https://github.com/obra/superpowers) | 可组合的需求澄清、计划、开发、验证方法 | 角色和任务方法按需启用；不自动把每个小任务升级为全套流程，也不据此获得用户未授予的委派权限 |
| [Spec Kit](https://github.com/github/spec-kit) / [OpenSpec](https://github.com/Fission-AI/OpenSpec) | 需求、设计、任务、变更归档的结构化材料 | 采用轻量变更包，关联中央任务 ID；不同时让两套工具各维护一份任务完成状态 |
| [Beads](https://github.com/gastownhall/beads) | 依赖任务图、可领取任务、原子认领、跨会话工作上下文 | 借鉴数据与交互模型。当前上游已使用 Dolt，不能再描述成纯 Markdown/JSONL 方案；本项目不增加 Dolt，协作事务仍由 PostgreSQL 管 |
| [MCP Agent Mail Rust](https://github.com/Dicklesworthstone/mcp_agent_mail_rust) | 异步协作消息、确认回执、文件预约、可审计归档 | 借鉴交接消息和预约。其文件预约是 advisory，不是安全锁，也不替代多租户授权；[原 Python 仓库](https://github.com/Dicklesworthstone/mcp_agent_mail)已标注由 Rust 版接替 |
| [Claude-Mem](https://github.com/thedotmack/claude-mem) | 自动观察、跨会话记忆、先取检索目录再展开证据 | 借鉴采集和渐进读取；不额外部署其 SQLite/Chroma 栈，不把个人记忆系统当作本项目的团队权限系统；不沿用其宣传的节省倍数 |
| [pgvector](https://github.com/pgvector/pgvector) | 在 PostgreSQL 中做向量检索、与关键词检索组合 | 在服务器测试后引入；先验证中文/代码查询和授权范围内的召回，不先建设独立向量集群 |

## 4. 项目组、仓库和权限模型

### 4.1 对象关系

```text
平台
├─ 超级管理员：创建管理员/项目，批准授权、新设备和扩权
├─ 项目组 A（继续使用现有 project_id 表示顶层协作空间）
│  ├─ 工程 Web → 独立仓库 → 模块、接口、路径
│  ├─ 工程 PC  → 独立仓库 → 模块、接口、路径
│  ├─ 业务资料范围 → 需求、业务结论、获准共享的工作记录
│  └─ 任务图 → 执行实例 → 每轮记录 → 检查点/交接
└─ 项目组 B：单独授权，不能从 A 的角色推导访问权
```

通用框架仓库独立于以上业务仓库，不能装入私有业务数据或服务器凭证。授权后的本机工作区是投影：有 Web 权限就只组装 Web；不为了显示“完整项目组”克隆 PC。

稳定资源 ID 与显示名称分开，重命名不改变授权。数据库关联带协作空间范围，防止把 A 的任务关联到 B 的检查点。嵌套工程、submodule、Git LFS、跨仓依赖同样需要显式登记和授权。

### 4.2 三种边界分别处理

```text
允许执行的修改 = 已批准资源权限 ∩ 本次专注范围 ∩ 任务批准范围
```

- **代码范围**：独立仓库的读/写能力；同一仓库内的路径限制是任务护栏，不是代码保密边界。sparse checkout 和 worktree 都不能把同仓代码变成“看不到”。
- **业务范围**：哪些共享日志、接口和需求可以阅读。获准读业务资料，不等于获准读全部代码、原始测试输出或技术日志。
- **专注范围**：工程、目标端、功能允许项/排除项、允许改动路径、验收条件、范围版本。用户明确说“取消专注模式”才能解除专注；解除也不能增加服务器权限或任务范围。

功能越界不能只靠路径判断：在 Web 仓库添加桌面打包依赖也可能越界。需要任务计划范围审查、依赖/产物差异检查与最终审查共同发现，不能承诺靠一个正则判定全部业务语义。

工作日志拆成两种视图：原始技术记录受来源工程权限约束；可共享的业务结论单独发布并有范围、来源和必要审批。混合来源的摘要要求读者满足全部来源权限；需要扩大可见范围时，发布经审定的独立资料，不能自动“脱敏即公开”。

### 4.3 Git 权限不能只在 MCP 里检查

生产受管路径建议使用 **Hub Git 访问代理 + 服务端 GitHub App**：客户端只拿本项目的 Hub 访问能力，GitHub App 私钥及上游令牌留在服务器，代理只访问登记的仓库与允许的 Git 操作，不成为任意 URL 代理。每次 fetch/push 都检查资格；正式接收和合并还检查任务代次及交付证据。

GitHub App 的安装令牌可以指定仓库和权限；不传限制参数会继承安装范围，因此服务端必须显式缩小范围。[GitHub 官方说明](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app)

代理是待开发组件，不是现有文档索引功能。若试点采用成员自己的 GitHub 权限直连，必须显示为直连模式，实施独立授撤权及定期核对；Hub 停权本身不会撤销外部账号、既存 SSH key 或另行取得的 Token。已开始传输、已下载副本也不能“撤回”。读文档用的只读仓库凭证不足以支撑开发推送。

### 4.4 人员与审批规则沿用已确认要求

管理员及平台项目只能由超管创建；项目管理员只管理被分配范围，可提交授权申请，不能自行生效。首次授权、扩权、新设备由超管批准，批准内容绑定版本/摘要；已批准会话可以自动续期。

管理员必须有已验证邮箱；普通成员邮箱可选。绑定邮箱的新设备先验证邮箱再经超管审批；无邮箱设备仍需审批。超管控制用户、设备和成员资格。平台可在批准范围内自动生成短期会话凭证，这不是让管理员绕过审批签发新权限。

角色名、提示词里的“架构师”、业务日志和本地配置都不能改变这些规则。

## 5. Skill 应怎样拆分

首版保留两个入口，不让安装和每天工作都加载 1,500 多行安装说明。

| 入口 | 触发 | 职责 |
|---|---|---|
| `agent-framework-setup` | 安装、接入已有工作区、修复安装或迁移框架 | 获取已批准清单，检查路径，安装已签名版本及适配器，建立本地导航和部署归属清单；不创建平台项目、不授予权限 |
| `agent-doc-memory` | 受管工程开工、恢复任务、开发、记录和交接 | 检查状态、恢复专注与相关记忆、按任务取证、形成逐轮工作笔记、交接；安装升级的机械动作交给客户端 |

架构师、开发者、审查者等保留为角色配置和按需方法参考，不必每个角色都注册一个常驻 Skill。原方案 `agent-project-workflow` 的日常职责并入 `agent-doc-memory`，避免两套同时维护记忆和任务。

目标仓库结构如下，这是待实现的发行结构，不表示目录已创建：

```text
framework-repo/
├─ skills/
│  ├─ agent-framework-setup/  # SKILL.md + 安装/迁移参考
│  └─ agent-doc-memory/      # SKILL.md + 专注/笔记/交接等按需参考
├─ adapters/                # 各宿主、系统、版本的配置与事件映射
├─ runtime/                 # 确定性的安装、记录、快照和清理组件
├─ contracts/               # 版本化协议、事件、范围、回执格式
├─ templates/               # main.md、角色、索引、工作笔记、变更包
└─ tests/                   # 协议、恢复、安全边界与宿主行为测试
```

`SKILL.md` 只包含适用场景、关键边界、日常流程和参考资料路由。通用技能仓库不保存项目专属记忆；业务经验也不能自动修改所有人的通用 Skill。知识推广先形成候选，经验证后再进入受控框架版本。

`agents/openai.yaml` 可提供 Codex 展示和调用元数据，但不是发现机制。不要复制七份会独立漂移的正文：构建发行包时从同一内容源生成宿主入口，每个已安装副本记录版本及哈希。[Agent Skills 格式](https://agentskills.io/specification)、[Codex Skill 官方说明](https://learn.chatgpt.com/docs/build-skills)

**不能先写一个要求调用不存在 MCP 工具的“正式 Skill”。** 先实现并公布能力契约，再发布匹配的 Skill/适配器；缺能力时给出明确状态，不改用文字“假装完成”。

### 5.1 原来的角色、链路和七个门控落到哪里

每个任务选择经批准的流程配置，而不是每轮对话重跑七个门控。保留原 G1—G7 的含义，把通过条件改成可核验产物：

| 门控 | 需要的依据 |
|---|---|
| G1 需求确认 | 已确认目标、验收和明确不做的事项，关联范围版本 |
| G2 设计评审 | 有版本的设计及评审记录，明确跨工程接口影响 |
| G3 可行性 | 依赖、环境、技术风险和必要验证证据；未验证假设不写成结论 |
| G4 开发准入 | 有效授权、当前执行代次、专注/任务范围、准备回执及适用的前置门控 |
| G5 代码质量 | 对确定快照的审查及实际检查结果；审查者有真实身份/执行实例 |
| G6 测试通过 | 测试对象与交付快照一致，记录运行方法、结果、环境及未覆盖部分 |
| G7 发布 | 已批准发行内容、适用证据、发布权限及回滚方式；部署是独立授权动作 |

小修复可使用项目批准的精简流程；明确记为“不适用”并附策略依据，不让 Agent 自行以任务简单为由跳关。范围或代码快照改变时，有关评审/测试证据需要重新核验。失败重试和超时按流程配置，达到上限后保全并上报，不无限循环，也不删除失败记录。

角色职责文档说明“如何工作、要交付什么”；服务器审批说明“谁有资格批准”。同一 Agent 扮演审查员可以自检，但不能冒充独立审查。对不开发代码的解释/查询任务，不强迫创建发布链路。

## 6. 使用者实际怎样操作

以下是目标体验，目前不是现有桌面按钮清单；现状仍见[使用指南](../使用指南.md)。

1. 超管创建项目组，登记各独立工程及业务资料，配置管理员和批准的开发范围。
2. 成员安装桌面端，用自己的账号登录，完成对应邮箱验证/新设备审批。
3. 桌面只展示获准项目组；选择工作目录和 harness，一次安装已批准框架及可访问的工程。
4. 用户说：“开始处理 Web 的登录超时，只做 Web，不增加 PC 功能。”日常 Skill 把范围整理为工作上下文；服务端验证其不能超出已授权资源。
5. 系统检查已批准发行版本、身份、已有任务和最近未完成记录，原子认领任务，取得当前记忆、关键约束、同事增量和检查点，保存准备回执。
6. 开发期间自动采集变更；每轮结束 Agent 只补一段简短的目的、原因、验证和下一步，客户端保存快照并上传。
7. 桌面区分“本地已保全”“服务器已接收”“可交接”“测试已验证”“任务已验收”，不能合成一个含糊的“已完成”。
8. 换电脑或换人，在授权范围内领取接续任务，恢复最新有回执的代码与笔记，重新检查当前权限和本机环境后工作。

不要求开发者手写目录前缀、维护共享 JSON、逐次复制同事聊天、反复回答已有配置。真正缺失的范围选择、权限审批、配置冲突或外部副作用仍需明确处理。

## 7. 每轮改代码必须有记录：可执行的设计

### 7.1 轮次与记录的定义

工作轮次是一个执行实例处理一次用户输入或一段有明确边界的自主工作；不是一次 Git commit，也不是“整个大任务结束”。每个轮次有稳定 `turn_id`，关联任务、执行实例、用户、设备和 harness。子执行实例单独标识，并关联父任务。

规则：**凡观测到代码、测试、配置、依赖或迁移改动，都要产生工作记录；失败、撤回、回滚到原样、取消和中断同样记录。** 单纯查询不强制写冗长日志；产生重要决定仍可追加决策记录。框架自己的日志、缓存和索引产出不再次触发“写日志的日志”。

### 7.2 三层记录，不是让模型写流水账

| 层 | 产生方式 | 内容 |
|---|---|---|
| 事实事件 | 客户端采集 | 轮次开始、改动文件、工具结果、快照 ID、实际命令退出状态、时间与主体 |
| 轮次工作笔记 | Agent 简写，缺失时明确标注 | 目标、改了什么及原因、验证、当前状态、风险和下一步 |
| 长期知识 | 后台按增量筛选和提炼 | 可复用决定、接口、约束、经验；有来源、适用版本和有效状态 |

笔记是可交接的解释，不是模型隐藏推理过程；默认不采集完整聊天、思维链或全量终端输出。测试证据应脱敏，标记来源和可信等级。Agent 自述“测试通过”不等于 CI 或客户端已观察到通过。

若用户说“不改业务文档”，不额外改业务 Markdown，但仍按已约定规则保存协作工作记录。若明确拒绝必要的工作采集，则说明该任务不能作为合规的受管开发继续，不偷偷上传或把它标记为已完成；保全已有本地工作并停止新增受管修改。

建议笔记模板：

```text
任务/轮次：由客户端填写
范围与快照：由客户端绑定，不由 Agent 自行声称
目标：本轮要解决什么
变化与原因：关键改动、必要的取舍或失败尝试
验证：实际执行的检查及结果；未执行则注明原因
当前状态：继续中 / 受阻 / 待审查 / 中断待补
风险与下一步：接手人下一件应做什么
```

笔记长度以能交接为准，一般几条即可。长任务在关键步骤、切换前和周期性检查点保全，不等一次数小时运行结束才上传。

### 7.3 记录状态机

```text
开始轮次，持久保存意图和基线
→ 观测修改并持续保全
→ 冻结一个确定快照，笔记/验证证据绑定该快照
→ 本地持久待传
→ 服务端校验与持久接收
→ 返回可查询的回执
→ 满足相应条件后允许受管交付/交接
```

关键实现要求：

- 首次修改前记录仓库提交、已有脏文件和工作区标识，不把用户原有改动误记为本轮成果；预存文件是否上传按已批准的采集范围处理。
- 同时采集宿主写工具、Shell 执行后的实际差异及文件系统事件；定期和轮次边界全量核对受管文件元数据/必要内容。仅匹配 `Edit/Write` 会漏掉终端写文件。
- 只比较首尾 `git diff` 会漏掉“改了又撤回”。需要保留中间事件与检查点；监测丢事件时记录覆盖缺口。任意外部工具的瞬时改写不能被文件监听绝对保证捕获。
- 支持受管启动的独立 worktree/工作目录；同一目录多个写执行者未隔离时，标记归属不明并阻止把成果自动归给某人。worktree 是冲突隔离，不是保密隔离。
- 快照包括必要的新增、删除、重命名、二进制与未跟踪文件，不仅是一段 patch。基准 Git 对象必须远程可达或一起保全；LFS/submodule 依赖也必须可恢复且有权限。
- 测试证据绑定测试实际使用的快照。测试后又改了文件，旧通过记录不能覆盖新快照。
- 本地使用受控、加密、可崩溃恢复的文件队列，不安装本地 PostgreSQL/Docker；落盘成功再确认本地保全，上传按内容哈希和幂等键重试。
- 正常轮次结束检查笔记。强制中止、断电或模型失败则保存可获得的事实并标记 `note_pending`；恢复后补说明，不能伪造“当时已写”。没有可靠轮次事件的客户端不能宣称完整逐轮覆盖。
- 退出 Hook 只做短时本地落盘；后台组件负责续传。不要在关闭编辑器的几秒内依赖大文件网络上传完成。
- 用户“停止”立即停止新工作，不因补笔记无限唤醒 Agent。离线可以保全和补传；未拿到远端回执就不显示“可交接”，不能进入正式完成/发布状态。

需要区分两个保证：服务器能强制“无合格记录不接受受管交付”；客户端覆盖是否完整取决于已验收的宿主版本、入口和运行状态。不能由一个 Stop Hook 承诺拦截整个操作系统上的每次修改。

## 8. 架构师拆解、多人认领及交接

架构师产出变更包：目标、不做什么、接口影响、工程范围、依赖、任务和验收。开发任务关联工程和业务资源；架构师的角色不允许替别人扩权。

主任务状态建议为：`draft → ready → running → review → done`，另有 `blocked/cancelled`；“交接中”和租约过期属于执行实例/交接作业，不将任务成果误删。

### 原子认领

认领请求带任务 ID、工作上下文、预期版本和幂等键；主体由认证会话推导。服务端在同一事务中检查资格、依赖、专注范围、有效执行者及冲突资源，创建执行实例，分配递增 `fence` 和租约到期时间。

实现时按固定顺序锁定有关成员资格/授权版本和任务行；撤权与普通提交使用相同的协调边界，使两者的先后可判定。任务只有一条当前执行引用，抢占/交接递增代次；不能用“先查未认领，再另起事务写入”的方式实现。跨服务返回的 `task_version` 用作条件更新，幂等记录与认领结果同事务提交。

同一任务同时认领只允许一个成功；另一个获得有权限查看的已占用状态，不能覆盖。**你本人在 Codex 领过，再在 Claude Code 领，也属于两个执行实例；超管身份不会默认绕过这条规则。** 要接续就交接，要并行就拆成不同任务；人工强制转交也要留记录并使旧代次失效。

租约按服务器时间续期。过期后旧实例不能继续提交正式结果；后来补传的工作进入历史/待核对资料，不覆盖新执行者。不同任务的写冲突按登记模块和路径资源协调，统一顺序加锁并检查重叠，不能仅比较两段 glob 字符串。

### 交接

交接需要：最近有效检查点、代码基准、未提交改动、当前范围、未完成事项、失败尝试、验证办法与必要依赖。接手人使用自己的身份，重新取授权和上下文；不继承前任 Token/私钥。

已经收到的同事日志不因作者离职而删除；接手人从最新已确认检查点开始，不必等待离线旧设备。但界面必须显示最后可恢复时刻和缺失部分，不能承诺恢复从未上传的改动。

受管 Git 提交、合并检查和任务完成均校验当前 `fence`、范围版本、准备回执和检查点。仅在 MCP 内拒绝“完成”而允许随意合并旧成果，不算形成闭环。

## 9. 文档、记忆、向量与 token

### 9.1 唯一事实源

| 数据 | 权威位置 | 其他形式 |
|---|---|---|
| 通用框架、正式代码与正式文档 | 各自 Git 仓库的明确版本 | 按提交归档的副本 |
| 已接收工作原文、任务事件、授权和认领 | PostgreSQL | Markdown 导出、看板 |
| 原文附件、可恢复工作快照 | 服务器持久制品 + 数据库校验回执 | 后续可换对象存储 |
| 知识卡片、模块摘要、向量 | PostgreSQL，可重建 | 按授权缓存到本地 |
| 本机路径、待传队列、部署归属 | 本机受控文件及服务端登记 | 设备不能把路径当作全局资源 ID |

不要把活跃任务状态在 Git 和数据库双向同步为两个“最终依据”。共享工作日志先追加到数据库，事务 outbox 安排 Markdown 导出，导出失败不丢日志。Git 中既有日志按原始来源导入，不能假装是平台当时采集的事实。

### 9.2 五层记忆

原始档案 → 有来源的知识卡片 → 当前模块/业务记忆 → 当前任务与交接状态 → 本地执行记忆。

卡片记录来源版本与位置、适用代码版本、确认状态、有效时间和取代关系。失败方案保留历史，不能混成有效决定；冲突显式呈现，不能按“最新一条”自动裁定。当前摘要从卡片和必要原文重建，不能无限对上次摘要再摘要。

本地 `main.md` 只保留获准资源的短导航和当前工作说明；`doc_index.json` 是可重建路由；有关角色、模块记忆和引用按需落盘。不把所有业务历史塞进 `AGENTS.md`，也不修改个人全局 Agent 记忆来存某个项目的秘密。

### 9.3 开工必读与检索分开

准备流程先读取明确关联的任务验收、专注边界、当前接口、有效关键决定、未解决阻塞、最近检查点及必要同事增量。**这些不是可被 top-k 相似检索漏掉的可选资料。**

随后按需要：授权过滤 → 任务/模块定位 → 标识符与关键词检索 + 语义检索 → 合并去重 → 先返回短目录/来源 → 批量展开有关证据。原文、片段、数量、标题、附件和缓存都执行同样的访问边界。

准备回执绑定执行实例、权限版本、专注版本、代码版本集合、上下文包和必读集合。它只能证明资料按该版本提供及被流程确认，不能证明模型在心理意义上“理解了”。关键理解通过方案和验收验证。

### 9.4 持续提炼和成本

- 新原文先可靠保存，再异步处理分块、索引、卡片和摘要；用内容哈希及来源版本复用未变化内容。
- 分别保存原文接收、索引、提炼和 Git 导出水位。Worker 落后时提供重要的未提炼增量，不能只返回一份过时摘要。
- 权限收紧、来源撤回、决策取代会使有关派生结果失效；发布摘要前再次检查来源状态，避免竞态把过期权限资料重新发布。
- 不向未批准的外部模型发送业务材料。后台模型任务也按资源范围处理；授权读代码不自动代表允许上传到任何第三方模型。
- 初始工作上下文可按 3,000—6,000 tokens 试点，证据按需追加。预算是待测默认值；关键限制超预算必须显示缺口并继续取证，不能静默截断。
- 同一会话按版本和水位复用；压缩/换设备后可以重建。存成本地文件再送给模型仍然消耗输入 token。
- 总费用统计包括开工、查询、后台提炼、embedding、重排和重试；不以“摘要更短”或某个开源项目的节省倍数代替质量验证。

### 9.5 是否使用向量

建议保留 pgvector 路线，但它排在原文保全、权限和检查点之后。先建立中文关键词、路径、接口名、错误码和短词基准，再比较加向量是否改善召回；无需再提供独立向量数据库。

初期在获准范围内做精确向量检索，规模需要时再评估近似索引/分区。pgvector 官方明确说明近似索引的过滤可能减少返回数量；不能通过扩大权限范围补齐结果。[过滤及多租户说明](https://github.com/pgvector/pgvector#filtering)

当前整仓 ZIP 文档同步的 32 MiB、1,000 篇及正文合计 8 MiB 限制不能支撑无限增长。后续需按已登记路径和提交增量枚举、分页读取、保存不可变版本，增加明确的上限、保留策略和导出检查，不能只放宽压缩包限制。

## 10. 协议与数据库最小实现范围

### 10.1 现有与新增能力分清

当前桌面 MCP 已有：`hub_check_version`、`hub_get_project`、`hub_list_progress`、`hub_get_document_index`、`hub_search_documents`、`hub_read_document`、`hub_report_progress`。最后一个是文本进度上报，不是认领、代码快照或合格逐轮记录。

下面是**待实现的逻辑操作契约，不是现在能调用的 MCP 工具名**。API/CLI/MCP 共用同一业务服务，不能各自实现权限判断。

| 逻辑操作 | 核心输入 | 结果和服务端约束 |
|---|---|---|
| 获取工作区清单 | 已登录身份、目标协作空间 | 仅返回获准资源、发行版本、配置能力和策略版本 |
| 开工准备 | 任务/执行实例、范围版本、代码版本、上下文水位 | 返回必读集合、摘要、必要增量和缺口；确认后登记准备回执 |
| 任务认领/续租/转交 | 任务 ID、预期版本、幂等键；续租带执行代次 | 原子处理，当前授权、依赖和范围均匹配；旧代次拒写 |
| 开始/记录轮次 | 执行实例、轮次 ID、事件序号、基线、笔记及证据引用 | 追加事实；相同键同内容返回同结果，不同内容冲突；不允许覆盖历史 |
| 上传/确认检查点 | 允许范围的文件清单、内容哈希、基准对象、分块 | 只有完整校验和持久化成功才产生可恢复回执 |
| 检索/展开证据 | 获准范围、来源版本、查询/证据 ID、预算 | 版本化片段、出处、覆盖与水位；任意 ID 重新鉴权 |
| 请求交付/完成 | 当前代次、范围版本、准备回执、记录/检查点/验证引用 | 校验记录完整性及门控；不能仅凭模型宣称完成 |
| 查询/执行收尾 | 登记设备、退出作业、部署 ID/代次、限定收尾证明 | 仅允许指定上传与清理回执，不恢复普通访问 |

小型、意图明确的 MCP 工具优于一个万能远程 Shell 或暴露几十个内部 CRUD。工具名及 schema 随契约版本发布，只广告已实现且当前授权的能力；每次调用仍重新校验，隐藏工具列表不是授权。

框架契约至少固化以下记录结构；字段以真实实现的版本化 schema 为准：

```text
WorkContext：project_id、resource_ids、task_id、focus_version、
             platforms、write_scopes、feature_allow/deny、policy_version
Run：run_id、task_id、user_id、device_id、harness_kind/version、
     workspace_id、runtime_epoch、fence、lease_until、state
WorkTurn：turn_id、run_id、sequence、baseline_snapshot、observed_change、
          note_revision、evidence_ids、final_snapshot、capture_coverage、state
CheckpointReceipt：receipt_id、checkpoint_id、run_id/fence、manifest_hash、
                   artifact_hashes、accepted_at、durability_state
```

客户端可提交观察事实，但服务器填写/核对主体、代次和接收状态，不能相信客户端自报 `durability_state=ready`。相同事件键绑定内容哈希；补充笔记以新修订引用原轮次，不能改写已接收历史。上下文准备、检查点和提交均有稳定关联，避免拿别的任务或旧快照回执充数。

### 10.2 新增实体族

沿用现有身份/审批表，分阶段补充：

- 工程、仓库、业务资料范围、资源授权、权限版本、外部 Git 访问登记。
- 任务及依赖、工作上下文、执行实例、租约/fence、写资源预约、准备回执。
- 轮次、不可变工作事件、笔记修订、实际验证证据、检查点、制品及回执。
- 原文版本、文本块、卡片与来源、摘要版本、embedding 模型版本、处理水位。
- 部署归属清单、发行清单、退出作业、逐项清理状态、事务 outbox。

任务的有效主执行者通过事务和唯一约束控制。主体从服务端认证推导；请求不能自行指定“我是谁”或任意租户。应用账号不拥有表、不带 `BYPASSRLS`；事务内设置上下文，连接归还不残留权限；Worker 的跨范围能力单独隔离。[PostgreSQL RLS 官方说明](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

上传与数据库不是一个原子存储：先建受限上传记录，分块暂存、校验并完成持久化，最后提交 `ready` 回执；故障重试或清理无主制品，不让数据库提前引用尚不存在的文件。幂等只能保证一次逻辑效果，不宣称网络消息只传一次。

服务端数据库恢复后更换运行 epoch，旧会话、准备回执和租约必须重新验证，避免备份恢复让旧执行代次重新获得写权。

## 11. 七种 harness 的跨端适配

共用协议，不假设共用配置文件。适配键至少包含产品、IDE/CLI/桌面形态、地区版本、操作系统、版本范围和运行位置。云端 Agent 无法直接连接用户电脑上的 stdio/loopback 服务，属于单独的远程接入，不纳入本机适配的自动结论。

| Harness | 本次官方资料核验 | 实现和验收边界 |
|---|---|---|
| Claude Code | 有 Skills 与生命周期 Hook；SessionEnd 不阻止关闭且时间有限。[Hook](https://code.claude.com/docs/en/hooks) | 验证输入、写工具/Shell、Stop、中断和恢复；不能只靠 SessionEnd 上传 |
| Codex | 支持生命周期 Hook，但部分工具路径、错误行为和信任配置存在边界；MCP Hook 不保证启动时连接就绪。[Hook](https://learn.chatgpt.com/docs/hooks) | 用可信本机组件可靠落盘；验证具体 App/CLI 版本，不把非阻断 Hook 作为唯一闸门 |
| Cursor | 有提示前、工具前后、编辑后和 stop 等事件；普通 Hook 失败可能放行。[Hook](https://cursor.com/docs/hooks) | 验证失败行为；Agent、Tab、云端不是同一组事件，分别登记覆盖范围 |
| Qoder | 官方 CLI 有 Skills/MCP 和 Hook，包括提示、工具、Stop 等。[Hook](https://docs.qoder.com/cli/hooks)、[扩展](https://docs.qoder.com/qoder/extension-publishing) | CLI 文档不直接证明 IDE/其他形态等价，按实际入口测试 |
| CodeBuddy | 官方有 Skills/MCP/Hook；Skill frontmatter Hook 有作用域与信任限制。[Hook](https://www.codebuddy.ai/docs/cli/hooks) | 不为安装框架全局放开所有未信任 Hook；IDE、CLI 分别验证 |
| WorkBuddy | 官方插件体系列出 Skill、MCP、Hook。[插件](https://www.codebuddy.cn/docs/workbuddy/Plugins)、[MCP](https://www.codebuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/MCP-Guide) | 本次资料不足以证明所有事件及阻断语义等同 CodeBuddy；需实机探测，不能直接复用目录/事件假设 |
| TRAE | 官方国内桌面文档列出 Skills/MCP、SessionStart、UserPromptSubmit、工具前后等 Hook。[Hook](https://docs.trae.cn/ide_hook-configuration-reference)、[Skill](https://docs.trae.cn/ide_skills?lang=zh) | 不把国内桌面能力自动推定为海外版/CLI；多配置合并要防重复事件 |

适配器应做能力探测并登记：轮次事件、工具事件、阻断语义、身份关联、可信启用状态、快照路径、重启是否生效。缺事件时可用文件监测和显式结束轮次辅助，但必须标明降低的覆盖能力。

Hook 的高优先级附加上下文仅放可信的框架控制信息、状态和资料引用。共享日志、仓库正文及其摘要通过普通资料/工具结果提供，明确是待核验数据；不能为了“强制读取”把任意同事文档直接变成高优先级指令。

每个组合只有三种发布状态：未支持、实验接入、受管验收通过。仅 MCP 连通属于实验接入，不代表“每轮强制记录、自动升级、撤权卸载”已验收。先验收少数明确组合再扩展，七种目标都保留，不虚报一次支持全部。

## 12. 登录、更新和退出

### 12.1 桌面是凭证与本机动作入口

优先沿用桌面登录 + 本机 stdio 桥接。凭证由 OS 受保护存储/现有安全存储处理，harness 配置仅保存连接和本机绑定，不放超管 Token、数据库密码或 GitHub App 私钥。控制 IPC 限于本用户、已登记绑定和操作；本机端口不能成为无需认证的任意文件/命令接口。

以后对外提供远程 MCP 时，按标准实现授权发现、OAuth/PKCE、受众与 scope 校验；不要把现有自定义设备登录直接称为标准 MCP OAuth。HTTP MCP 授权与本机 stdio 是不同接入面。[MCP 授权规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)

### 12.2 对话开始先检查版本，但不能让更新毁掉工作

分别维护桌面版本、框架发行版、适配器版本、协议版本和数据 schema 版本；不是只升级 Electron ZIP。

用户要求“落后先更新”落实为：开始/恢复受管工作时，比对**超管批准的稳定渠道**，有适用新版则先进入保全—校验—更新—重启/重新信任—自检流程，再开放工作。不是追踪 GitHub `main` 或每个上游最新版。

发行包有签名、哈希、支持平台、协议兼容范围和迁移说明；先暂存校验，再切换，失败可回滚到服务器仍允许的版本。保持本地定制，冲突显式处理。不覆盖未上传工作，不绕过宿主对更新 Hook 的信任要求。

网络失败、版本不兼容、签名错误时停止新的受管开发/交付，但保留状态查询、停止、保全、补传与受限收尾入口。更新系统不能锁死数据抢救通道。

### 12.3 撤权后的状态机

```text
资格撤销，普通请求与续租拒绝
→ 吊销旧执行代次，建立限定收尾作业
→ 受管客户端停止新工作，保存最终一致快照
→ 通过独立收尾通道上传
→ 服务端完整校验并返回有效回执
→ 按部署清单清理
→ 逐项确认 removed / pending / conflict
```

Agent 收到明确的结构化状态：停止普通任务、保全工作、调用指定收尾能力、等待有效回执再清理；脚本执行确定性的上传和卸载。**不能让 MCP 返回一段任意 Shell 再要求 Agent 盲目执行。** 客户端独立处理通知和状态，即使当前 Agent 忽略文案也不能继续获得正常服务。

收尾能力在设备部署时登记，只绑定设备/项目/作业/允许上传对象，具有配额、有效期和独立吊销方式；即使账号被禁用，也能按策略恢复该设备的收尾，不接受匿名无限上传。安全事件中超管可单独冻结可疑收尾渠道，此时显示未回收缺口。

上传失败或断网：普通权限已停，文件和队列保留并重试，不提前卸载。没有持久回执、快照与最新工作不匹配、清理中又出现改动，均不能伪报清理完成。

清理范围覆盖登记的完整框架：Skill、角色/文档投影、脚本、框架测试、缓存/本地派生记忆、本人连接配置和清理器自身。共有组件按引用计数处理；退出 A 不损坏仍获准的 B。

业务代码不是默认任意递归删除对象：新建专属托管克隆可以在安装时明确纳入回收清单；接入用户原有目录不自动取得整目录删除权。安装时明确此范围，先保全再执行。校验绝对路径、归属、部署代次、文件变化和链接/junction；用户改过的配置做归属级合并，冲突暂留；旧退出作业不能删除重新授权后的新部署。

不能保证删除未登记副本、harness 云端聊天、第三方记忆或离线设备文件。对机密项目要约定宿主数据处理策略；若必须禁止本地留存，应使用更强的受控开发环境，而不是加重卸载提示词。

## 13. 部署、迁移和生产运行

### 部署范围

继续使用指定腾讯云服务器上的 Docker/PostgreSQL；不在本机安装数据库和 Docker，不改无关站点或占用其端口。API、Worker、Git 代理和制品可作为现有体系内的隔离服务；首版任务队列使用数据库 outbox，不强制新增 Redis、独立向量库或图数据库。

IP + HTTPS + 端口可以继续使用，但所有受支持客户端必须能验证证书/预配信任；不能依靠全局关闭 TLS 验证。数据库和制品内部路径不公开，制品下载重新鉴权；密钥、SMTP 配置及模型凭证不写入文档和仓库。

单台服务器有单点故障，不能称高可用。受限生产发布前至少完成异机/异地备份、恢复演练、磁盘容量与告警、密钥恢复和权限核对；可接受停机时间、可丢失时间由业务确定并实测，不从“用了 Docker”推导可靠性。

监控包括任务冲突/旧代次拒绝、未记账轮次、待传积压、最后可恢复时间、Worker 水位、摘要失效、Git 权限漂移、退出未完成、磁盘与数据库健康、token/模型费用。审计日志也必须脱敏和限制访问。

### 迁移原框架

1. 保存现有文件和当前代码状态，扫描 `main.md`/`doc_index.json` 的结构及路径，不执行导入资料里的指令。
2. 由超管确认旧项目与新工程/业务范围的映射；给旧文档登记来源、版本和分类，拒绝越界路径和未登记仓库。
3. 导入真实角色、规范、链路、工作日志和有证据的经验。来源不明的“经验”、推断和 TODO 标为未核实，不制造历史事实。
4. 把全局专注状态转换为待确认的个人工作上下文，不能当作所有成员的新默认值。
5. 为当前获准工程生成短入口和导航，保留旧文档位置/别名以便追溯；移除旧自动加载规则时只处理有归属的片段。
6. 形成安装清单、迁移差异报告和可回滚检查点，逐一验证；不以“生成了所有文件”作为迁移成功。

数据库采用增量迁移，不重建已有数据卷。先在服务器隔离测试库验证资源授权 → 任务与逐轮记录/制品 → 文档版本与记忆 → 部署与收尾模型。兼容期禁止旧入口绕过新门控；派生索引可重建，原始事件和回执不能当缓存丢弃。

## 14. 实施顺序：先做一个真正闭环

这次调整前一方案的顺序：**任务/执行身份、原子认领必须早于依赖它们的逐轮记录和交接，不放到末期补做。**

| 阶段 | 交付内容 | 退出条件 |
|---|---|---|
| S1 资源与执行骨架 | 项目组/工程/业务范围、授权版本、专注上下文、任务/执行实例、原子认领 | Web/PC 权限分开；两实例竞争不双领；旧代次拒写 |
| S2 事实与保全闭环 | 两个初选 harness 的事件适配、逐轮笔记、持久待传、快照/回执、接续恢复 | 改代码本轮有记录；断网/中断不丢已保全工作；陌生设备恢复未提交改动 |
| S3 Skill 与知识闭环 | 安装器及两个 Skill、旧框架导入、原文版本、必读集合、增量摘要、关键词/pgvector 对比 | 按授权安装；开工恢复同事有关工作；来源可追溯；重要旧事实不漏 |
| S4 控制与回收闭环 | Git 访问闭环、正式交付门控、完整框架更新、撤权收尾和卸载 | 绕过旧入口不能正式交付；停权后只收尾；持久回执前不删；更新失败可恢复 |
| S5 生产资格 | Windows/macOS 实机组合、长期历史、性能/费用、备份恢复、安全与运维 | 每个发布组合有版本化验收证据；未通过组合仍标实验；七种全通过才能宣称完整支持 |

S1—S3 可以进行隔离试点，但 S4 和对应 S5 未通过前不称受管生产版。先完成两个明确宿主组合的闭环，再扩展其余组合，不取消七种 harness 和双系统的最终要求。

首个纵向试点建议为：同一业务下 Web 与 PC 两个独立测试仓库，成员只有 Web 代码权和业务日志权；两个 harness 同时认领一个 Web 任务，获胜者修改并保全未提交代码；换设备恢复；撤权；受限补传；完整清理。不要第一轮就在未知状态的真实私有仓库做卸载测试。

`kms` 目前只确认私有仓库地址，不据此推定分支、工程划分、资料目录或已配置凭证。真正接入前，由超管在后台提供这些映射；开发凭证与文档只读凭证分开，秘密无需放进聊天。
