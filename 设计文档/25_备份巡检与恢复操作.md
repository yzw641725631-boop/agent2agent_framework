# 备份、巡检与恢复操作

2026-11-09，适用于服务器 `47.109.23.86`、后端 0.7.0。这里是运维操作说明，使用流程见[安装与使用指南](../使用指南.md)，功能验收见[24 号记录](24_持久代码交接与恢复验收.md)。

## 已启用的任务

所有日历时间按服务器的 **Asia/Shanghai** 时区解释。定时器已在实际 systemd 219 验证，不使用其不支持的 UTC 时区后缀。服务器重启后会补执行错过的日历任务。

| 任务 | 计划 | 成功依据 |
| --- | --- | --- |
| `agent-hub-backup` | 每日 03:15，附少量随机延迟 | `last-success.json`：已完成加密快照及全仓库数据读取检查 |
| `agent-hub-archive-audit` | 每日 02:15，附少量随机延迟 | `last-archive-audit.json`：逐个解密核验、缺失/孤儿/容量报告 |
| `agent-hub-restore-drill` | 每月 1 日 04:15，附少量随机延迟 | `last-restore-drill.json`：实际新建临时库、还原备份、核验制品，通过后清理 |
| `agent-hub-ops-check` | 每五分钟 | `last-ops-check.json`：运行状态、备份时效、磁盘、更新清单；错误返回非零 |

状态文件均位于 `/opt/agent-hub/backups`，仅 root 可读。巡检不会返回业务记录、环境变量、SMTP 或数据库密码。`healthy: true` 仅表示本机巡检项没有错误；`has_warnings: true` 的异地备份与外部告警缺口仍需处理。

人工执行一次：

```sh
systemctl start agent-hub-backup.service
systemctl start agent-hub-archive-audit.service
systemctl start agent-hub-restore-drill.service
systemctl start agent-hub-ops-check.service
systemctl list-timers --all --no-pager
cat /opt/agent-hub/backups/last-ops-check.json
```

备份与恢复共用 `backup.lock`，同一时刻只运行一个；锁忙时保持失败状态，运维人员核对已有任务后重试。巡检不会自行清除失败状态、修复损坏快照或删除代码。

## 巡检判定

- API、入口、PostgreSQL 健康状态，文档 Worker 是否仍在运行；数据库实际执行 `SELECT 1`，公网 HTTPS 校验证书并读取健康接口。Worker 的业务作业是否前进仍需独立作业监控。
- 最近备份、制品巡检不得超过 36 小时，恢复演练不得超过 45 天；结果必须完整成功，缺失、损坏、链接或来自未来的状态文件均判为错误。
- 对应 service 失败，或 timer 未加载、未运行，即使旧成功记录仍新鲜也报错。
- 磁盘剩余少于 4 GiB 或 5% 报错；剩余低于 15% 提醒。当前正式制品全站配额为 **4 GiB**，每项目默认 **1 GiB**，不能按应用默认 16 GiB 估算当前容量。
- 更新清单通过内置公钥验证，剩余不足 72 小时提醒，签名无效、到期或无法访问报错。私钥仍只在发布机，不能为了续期放到 API 服务器。

没有异地连续备份目标与独立外部告警时，报告持续显示警告。服务器自身的巡检无法发现整机断电后再通知你，不能把 systemd journal 当作可靠送达的通知系统。

## 备份内容与权限

restic 仓库位于 `/opt/agent-hub/backups/restic`，密码单独存放在同目录的 `restic-password`，仅 root 可读。固定镜像摘要见[备份脚本](../projects/agent-hub/deploy/backup-server.sh)。

每次备份包含一致性 PostgreSQL custom dump、角色定义、完整代码制品、应用与数据库配置。应用配置含制品解密密钥，因此同样放入 restic 加密仓库；不要把还原出的配置上传 Git、下载站点或聊天。**当前备份不包含 TLS/ACME 状态、其他宿主服务或完整服务器镜像**；新主机的入口需从部署模板和受控证书配置重建，另行验收。

备份容器只读挂载业务源；为读取 uid 10001 的 0700/0600 制品，只有备份过程增加 `DAC_READ_SEARCH`。恢复容器只写独立演练目录，为恢复属主增加 `CHOWN`、`DAC_OVERRIDE`、`FOWNER`，正式应用的 capabilities 未扩大。

restic 退出 3 可能已留下不完整快照。脚本只在完整备份及读取检查成功后更新 `last-success.json`；恢复演练固定使用此记录的 **确切 snapshot ID**，不用可能指向失败尝试的 `latest`。[restic 退出状态](https://restic.readthedocs.io/en/stable/040_backup.html#exit-status)、[恢复指定快照](https://restic.readthedocs.io/en/stable/050_restore.html)

## 本次异地副本与密钥保管

已把一份正式 restic 加密仓库复制到本机 `D:\agent_cache\agent-hub-recovery\server-47` 并核对 SHA-256；密码的独立副本在 `D:\agent_cache\codex\secrets\agent-hub\restic-server-47-password`。两处均在框架仓库外，ACL 限当前 Windows 用户和 SYSTEM。密码未写进源码、安装器或验收报告。

这只是一份 **2026-11-09 的人工异地副本**，不会持续接收后来代码。长期仍需独立故障域的对象存储或备份机、受控凭证、定时复制、备份成功确认及从异地恢复的演练。尚未配置自动删除历史备份；容量巡检只是发现风险，不能替代经过确认的保留与清理策略。

## 恢复失败时怎样处理

1. 查看对应 service 的 `Result`、退出码及 journal。状态报告不回显命令的异常正文，完整排查只在受控服务器进行。
2. 恢复演练只操作 `hub_restore_时间戳` 数据库和 `/opt/agent-hub/backups/drills/时间戳`；失败时保留该次副本，不覆盖正式库。先确认目标路径和数据库名，再单独清理，不能递归删除备份根目录。
3. 制品校验失败时，保持原回执与原文件，隔离损坏副本，按确切日志与快照 ID 从可信备份恢复。不能重发一个成功回执掩盖内容丢失。
4. 事故恢复到新主机需要先核验加密仓库、恢复角色/密钥/数据库及文件属主，再启动匹配应用和 HTTPS 入口，确认授权状态及资料恢复后开放访问。这套全新主机流程仍需实际演练；现有证据是临时数据库与独立制品目录的恢复。

升级前 dump、上一版应用和代码卷应共同保留。0010 禁止自动 downgrade，避免回滚应用时误删交接证据；应用降级也不应删除数据库新表或制品目录。

## 宿主系统的生产条件

当前宿主仍是 CentOS 7。上游支持在 2024-06-30 结束，兼容旧 systemd 只解决定时任务运行，不能恢复操作系统安全维护。[CentOS 官方生命周期](https://centos.org/centos-linux/)

生产扩展前应准备受支持的新宿主，先完成备份恢复和入口验证，再安排受控切换。现有主机还运行其他服务，不能把本项目的部署授权扩大成原地升级或重装整台服务器的授权。
