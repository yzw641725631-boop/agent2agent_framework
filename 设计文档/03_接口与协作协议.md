# 接口与协作协议

> v0.2｜2026-11-05｜完整目标的建议契约；示例 ID 为占位值，正式接口使用 UUID。P1 已实现路径及阶段差异见[实施记录](06_实施记录.md)。

## 1. 统一约定

- 服务器对外使用 HTTPS。管理界面与 MCP 共用业务授权层。
- 人员登录采用成熟 OAuth 组件实现标准流程，原生应用使用授权码与 PKCE；MCP 的协议和授权版本在连接时协商。
- 首版受管设备通过本地桥接器调用服务器，并提供设备密钥证明。原生客户端未达到同等约束前不开放静态 Token 直连旁路。
- 每个请求带请求 ID；修改操作带幂等键和预期版本。超时后先按幂等键查结果，不能直接重复执行。
- 调用者身份来自已验证凭证；不能通过参数指定他人身份、数据库角色或任意文件路径。
- 未授权跨项目对象返回统一错误。搜索、资源读取、下载和导出使用相同授权规则。

后文 JSON 展示应用数据体，MCP 的 JSON-RPC 包装、版本元数据等由官方 SDK 和兼容层实现；不将示例当作完整线协议报文。

## 2. 管理与登录接口

| 方法及路径 | 权限 | 功能 |
|---|---|---|
| POST /api/admin/users/admins | 超管 | 创建管理员账号 |
| POST /api/admin/projects | 超管 | 创建项目 |
| PUT /api/admin/projects/{id}/administrators | 超管 | 分配项目管理员 |
| POST /api/projects/{id}/member-invitations | 超管或本项目管理员 | 邀请普通成员，首次访问仍需审批 |
| POST /api/grant-requests | 范围内申请者 | 申请首次授权或增加权限 |
| POST /api/admin/approvals/{id}/decision | 超管 | 批准/拒绝，必须匹配申请版本及哈希 |
| POST /api/devices/enrollments | 已登录用户 | 绑定待审批设备公钥 |
| POST /api/devices/{id}/email-challenges | 本人 | 向已验证邮箱发送该设备验证码 |
| POST /api/devices/{id}/email-verifications | 本人 | 验证并消费该设备验证码 |
| POST /api/admin/devices/{id}/decision | 超管 | 审批新设备 |
| POST /api/projects/{id}/members/{user_id}/revoke | 超管或范围内管理员 | 撤销成员资格并创建退出作业 |
| POST /api/admin/users/{id}/status | 超管 | 冻结、停用或恢复账号状态 |
| POST /api/admin/devices/{id}/revoke | 超管 | 撤销设备及其正常会话 |
| GET /api/audit | 按角色和项目过滤 | 查询操作记录 |

项目管理员不能创建管理员、任命另一个项目管理员或批准签发申请。普通成员的角色增加需要产生审批申请；状态恢复也必须重新核验授权，旧令牌不自动复活。

OAuth 标准端点与元数据由所选认证组件提供，不用上述 REST 路径替代 OAuth 协议。绑定邮箱不能绕过超管审批；审批也不能跳过已绑定邮箱的新设备验证码。

邮件验证码默认建议为短期、单次使用，限制发送频率和失败次数。具体时长在实现时配置；发信失败显示待验证，不能把发送成功视为验证成功。

## 3. MCP 与本地工具

| 工具 | 执行位置 | 功能 |
|---|---|---|
| session_status | 服务端经桥接器 | 本人设备、当前项目授权和退出状态 |
| project_context | 服务端 | 当前获授权项目的入口、角色、相关文档和任务 |
| document_search | 服务端 | 在授权项目内检索，返回版本化片段 |
| document_get | 服务端 | 按文档 ID 和版本读取 |
| document_propose | 服务端 | 基于内容哈希提交文档变更提案 |
| task_list | 服务端 | 查看获授权且满足筛选条件的任务 |
| task_publish | 服务端 | 有 architect 能力的成员发布已版本化任务说明 |
| task_claim | 服务端 | 原子认领并返回执行代次与租约 |
| task_checkpoint | 服务端 | 保存执行进展及代码/制品引用，可同时续租 |
| task_handoff | 服务端 | 保存交接并转移主执行权 |
| task_submit | 服务端 | 提交待审查结果，检查当前资格和 fence |
| closeout_prepare | 本地与服务端 | 校验退出作业，冻结本地框架工作并生成快照清单 |
| closeout_upload | 本地调用受限 HTTPS 接口 | 分块上传，不把大文件编码进 MCP 文本 |
| closeout_status | 服务端 | 查看上传、回执和清理阶段 |
| cleanup_execute | 本地 | 以本地登记清单和服务端回执执行退出清理 |
| cleanup_report | 服务端 | 回报步骤结果，完成或标记部分失败 |

工具能力不等于授权。可使用固定的工具名称集减少宿主缓存差异，每次执行仍检查权限；本地清理工具只接受部署 ID、作业 ID 和回执，不接受任意 Shell 命令。

各工具声明准确的只读或破坏性提示。宿主自己的操作权限仍需适配；安装阶段登记已授权的框架退出策略和有限执行范围，不能通过关闭全部宿主权限检查获得兼容。

## 4. 文档协议

`document_search` 的建议请求：

```json
{
  "project_id": "project-a",
  "query": "登录接口 已知问题",
  "kinds": ["design", "experience"],
  "limit": 10
}
```

每个结果包含 `document_id`、`repo_id`、`relative_path`、`git_commit`、`content_hash` 和命中片段。服务端限制最大页大小，游标绑定查询和授权上下文，不能使用分页游标穿越到其他项目。

`document_propose` 必须提供当前基准哈希；基准过期返回版本冲突与有权访问的新版本引用。提交候选文档不自动改写项目规则或成为合并版本。

## 5. 任务协议

### 5.1 发布与认领

任务说明包括稳定任务 ID、输入资料、依赖、写范围、接口约定、验收标准和产物要求。说明已进入登记的 Git 提交后，发布事务建立可执行任务；依赖不满足时显示 blocked。

建议认领请求：

```json
{
  "project_id": "project-a",
  "task_id": "task-023",
  "run_id": "run-device-a-session-1",
  "expected_task_version": 7,
  "idempotency_key": "claim-request-001"
}
```

认领结果示例：

```json
{
  "status": "claimed",
  "attempt_id": "attempt-006",
  "fence": 8,
  "lease_expires_at": "2026-11-05T05:30:00Z",
  "task_version": 8,
  "allowed_write_scopes": ["auth-api"],
  "base_commit": "0123456789abcdef0123456789abcdef01234567"
}
```

第二个认领者收到 `TASK_ALREADY_CLAIMED`。即使两个执行者属于同一账号，也要通过显式交接切换；超管的执行实例同样受任务并发规则约束。

写范围第一版优先使用清晰的模块 scope_key；路径声明辅助发现重叠。服务声明不能阻止脱离框架的本地编辑，分支隔离和审查仍是结果准入的一部分。

### 5.2 检查点与接手

检查点至少保存：base/head 提交、已推送分支或已接收快照、完成项、失败尝试、测试命令和结果、下一步动作。仅填写本地绝对路径不构成交接。

交接先确认产物可被下一执行者访问，再转移 owner 并增加 fence。所有提交、状态修改和租约延长都带当前 attempt 与 fence；旧执行者不能覆盖新执行者的结果。

租约默认值在实现阶段配置。首版不以常驻客户端心跳为前提；任务步骤和检查点请求负责续租，长时间本地工作可显式申请合理租约。到期后的新认领仍会增加 fence。

### 5.3 提交与审查

`task_submit` 接收提交 SHA、快照引用和验证证据，进入 review。审查和合并是否允许由角色、门控和 Git 分支规则共同决定。状态 done 需要满足该任务的验收条件，不能仅依据工具调用成功。

## 6. 权限撤销协议

### 6.1 正常权限先失效

撤销事务提交后，下一次正常项目请求不返回项目数据，而返回稳定的业务退出状态。保持必要身份识别和有限恢复通道，避免简单失效登录凭证后 Agent 只收到反复登录提示。

MCP 调用结果建议包含 `isError: true`，在 `structuredContent` 中给出以下应用对象，同时提供清楚的文本退出指令：

```json
{
  "code": "PROJECT_ACCESS_REVOKED",
  "project_id": "project-a",
  "deployment_id": "deployment-01",
  "closeout_job_id": "closeout-01",
  "required_action": "closeout_and_uninstall",
  "allowed_actions": ["closeout_prepare", "closeout_upload", "closeout_status", "cleanup_execute", "cleanup_report"],
  "normal_operations_allowed": false,
  "requires_durable_receipt_before_cleanup": true
}
```

此对象不直接包含长期凭证、脚本正文或任意本机删除路径。身份完全无效的请求仍按标准返回认证错误；已登记设备可通过签名挑战访问退出恢复端点，查询仅属于自己的既有退出作业。

### 6.2 给 Agent 的退出指令

> 项目授权已撤销。当前项目进入强制退出状态。立即停止该项目的开发、资料读取、任务认领和常规提交。必须保存并上传现有工作及交接记录；取得服务器接收回执后，调用已登记的项目框架卸载脚本，并回报逐项结果。失败时报告真实状态，保留待收尾记录，不得将未完成的上传或清理报告为成功。

指令针对已授权管理的框架部署。脚本通过固定清单与凭证检查执行；指令文字不替代服务端授权，也不扩大到任意本地目录。

### 6.3 独立收尾通道

- `POST /api/device-control/challenges`：领取短时随机挑战。
- `POST /api/device-control/closeout-status`：以已登记设备密钥证明身份，只读取本人退出作业。
- `POST /api/closeouts/{id}/upload-sessions`：创建范围受限的快照上传。
- `POST /api/closeouts/{id}/upload-sessions/{upload_id}/finalize`：请求核验并签发持久接收回执。
- `POST /api/closeouts/{id}/cleanup-reports`：上报清理步骤和终态。

这些路由验证设备证明、重放标识、作业归属、动作和配额。设备即使已被撤销正常访问，也只保留原先批准的退出能力；不能借此恢复项目资格或读取新资料。

收尾凭证短期有效，可以在同一已授权退出作业内重新领取以完成断点重试。其权限上限在首次授权时获批，自动恢复不新增项目读取或开发权限。

## 7. 错误、恢复与审计

| 状态 | 客户端处理 |
|---|---|
| APPROVAL_PENDING | 展示申请编号，等待超管；不访问项目数据 |
| EMAIL_VERIFICATION_REQUIRED | 完成指定邮箱挑战，不重建审批范围 |
| DEVICE_APPROVAL_REQUIRED | 等待设备审批，不用通用 Token 绕过 |
| PROJECT_ACCESS_REVOKED | 进入退出协议 |
| TASK_ALREADY_CLAIMED / WRITE_SCOPE_CONFLICT | 展示获授权的冲突信息，选择其他任务或协调 |
| STALE_EXECUTION_FENCE | 停止该执行实例提交，查询交接状态 |
| DOCUMENT_VERSION_CONFLICT | 基于新版本重新提出变更 |
| UPLOAD_INCOMPLETE / RECEIPT_NOT_READY | 保留工作，恢复或重试上传；禁止提前清理 |
| CLEANUP_PARTIAL / HOST_PERMISSION_BLOCKED | 报告尚未完成项，等待后续重试；正常权限保持撤销 |

每个审批、认领、接手、撤销、回执与清理步骤写入带请求 ID 的记录。项目管理员只能查询自身项目范围；超管可查看全局。日志屏蔽验证码、凭证和私钥。
