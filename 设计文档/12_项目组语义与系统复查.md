## 1. 本次澄清修正了什么

用户创建的“项目”可以代表一项独立工程，也可以代表一个项目组或项目集群。原框架的重点包含组内跨子项目开发与协同。`install.md` 中共享入口、角色、模板、规范、知识与多个项目目录需要保留这种能力。

先前把接入流程围绕单仓库、单目录展开，缩窄了原意。身份、审批、桌面桥接等现有基础仍可复用，业务模型和安装入口需要补上项目组层级。

| 名称 | 含义 | 边界 |
|---|---|---|
| 平台 | 超管管理的全部协作空间 | 全局账号、设备、审批及运维 |
| 项目组／协作空间 | 用户在平台创建的一个顶层项目 | 管理员、成员、共享规范及授权边界 |
| 子项目 | 项目组内的具体工程或模块 | 职责、代码、知识、依赖及任务范围 |
| 仓库 | 版本化代码或文档的 Git 来源 | 用户选择 Skill 和各工程独立仓库；一个项目组使用多个获准仓库 |
| 工作区 | 某台设备上的实际工作目录 | 路径属于本机；结构可以容纳一个或多个获授权子项目 |
| 执行实例 | 某人、某设备、某 harness 的一次任务执行 | 同一个人的不同 harness 也需要参与任务竞争控制 |

单体项目可以是只有一个子项目的协作空间。这里的“项目集群”不自动意味着需要部署新的 Docker 或 Kubernetes 集群。

## 2. 原 install.md 应当处于什么位置

它是整个项目组框架的部署规范。它生成的组级入口、角色体系、知识和流程，是开发协作所需的实际工作环境。

建议保留三个配合的入口，后续实现时复用原模板，避免分别维护多套规则。

- `install.md` 保留安装约定、结构和原始规范，并说明接入前提。
- 安装 Skill 负责检查工作区、恢复已有部署、调用安装脚本、生成宿主配置并登记归属。
- 日常 Skill 负责恢复组级和子项目上下文、按任务范围协作、沉淀知识、上报进度和处理退出。

MCP 提供权限、版本、文档、任务及退出工具；PostgreSQL 处理审批和并发状态；Git 保存文档与代码版本。Skill 中的文字不能自行签发服务端权限。

## 3. 复查结果

| 优先级 | 问题与源码依据 | 实际影响 | 后续处理 |
|---|---|---|---|
| 阻塞项目组落地 | `models.py` 的 `DocumentRepository` 以 `project_id` 为唯一主键，后台也只有一份仓库配置 | 一个组暂时只能索引一个文档仓库；多个仓库无法分别登记和同步 | 增加子项目及仓库实体，按仓库保存配置、同步与快照 |
| 阻塞项目组落地 | `Project` 只有顶层项目信息，缺少子项目、仓库映射及依赖；`Controller.bind` 只登记项目 ID 和本机目录 | 原 `projects/` 中的多个工程没有对应的平台关系，也不能校验本地目录是否接错 | 先明确组、子项目、仓库与工作区映射，保留现有顶层 ID 的兼容性 |
| 阻塞安装衔接 | `workspaces.cjs` 和桌面“安装”动作仅处理 `.mcp.json` | 写入 MCP 后没有生成 `main.md`、角色、流程、记忆 Skill 或部署清单 | 建立完整框架安装流程，界面分别显示连接和框架部署状态 |
| 阻塞远程上下文恢复 | `document_worker.py` 只接收 `.md` / `.markdown`；`hub_get_document_index` 返回仓库索引状态 | 原来的 `doc_index.json` 不能通过现有文档工具读取；其路径映射也未被转换为组级上下文 | 增加经过验证的结构化入口及映射，保留原 JSON 的本地兼容；不能把任意 JSON 当可执行配置 |
| 阻塞任务协作 | 当前 MCP 只提供进度报告，`ProjectProgress` 没有执行所有权约束 | 同人多设备或多个成员仍可同时开发同一任务 | 实现任务原子认领、租约、执行代次、资源范围与交接 |
| 多设备冲突 | 原 `install.md` 把当前活跃／专注项目写入共享 `main.md` | 两个设备或 harness 会修改同一状态，可能互相改变上下文 | 共享入口记录项目组结构；当前选择和专注状态按设备／会话保存 |
| 权限模型缺口 | 当前 grant 只有顶层 `project_id` 和能力集合，没有子项目或仓库资源范围 | 不能表达“只准开发组内某子项目”；给组增加资料时也必须判断是否扩大既有授权 | 授权申请覆盖批准的资源集合／版本；接入新资源时重新核对审批，不能靠命名隔离 |
| 跨仓库版本缺口 | 当前文档按一个仓库提交和路径引用，`ProjectDocument` 键为项目加路径 | 多仓库都会有 `README.md`；跨项目接口资料还可能来自不相容版本 | 引用至少携带组、仓库、路径、提交；组级上下文记录所用各仓库快照集合 |
| 共享知识闭环缺口 | 文档工具只读，索引由管理员人工触发；进度报告只保存文本及可选提交号 | 本地新经验和代码不会自动出现在其他设备；只发进度不能交接未提交工作 | 文档修改走 Git 提案／合并及同步，另建检查点和未提交快照上传流程 |
| 更新范围缺口 | `updater.cjs` 更新桌面应用版本目录 | 已实现的是桌面及打包 MCP 更新，尚不能更新项目内由 install 生成的框架 | 区分客户端、框架发行、部署清单和文档 Git 版本；框架迁移核对归属并保留人工修改 |
| 退出未闭环 | 当前 MCP 初始化说明明确上传卸载未提供 | 撤权能拦截受管服务，未完成用户要求的自动上传及完整卸载 | 补独立收尾身份、持久队列、上传回执及按清单清理；组共享文件按引用处理 |
| 使用入口误导 | 原规范引用 `install-wizard.html`，当前目录不存在；根目录也没有已生成的 `Agent文档/` 与记忆 Skill | 用户无法按“打开向导”开始，也容易误以为平台源码已完成原框架部署 | 写清现有入口和目标流程；提供真实安装能力后再宣称向导可用 |
| 发行与运维待验收 | 当前记录的验证主要是 Windows，同一工作站的两套身份及升级前备份 | 不能据此宣布双系统、七种 harness、真实双设备协作和完整恢复已通过 | 按原验收矩阵继续实机验证，并补定时／异地备份和恢复演练 |

以上有些是功能缺失，有些是多设备下的规范冲突。现有单仓库阅读和进度报告功能并不因此失效。

### 3.1 需要保留的实际边界

组内跨子项目协作需要明确任务范围，组外访问需要相应授权。Markdown 中的角色名、目录前缀或“已批准”文字不代替服务端审批。

Hub 授权与 GitHub 直接访问是分别存在的。撤销 MCP 权限不会自动撤销已有 GitHub 账号权限。已复制到本地的文件和 harness 自带的终端能力，也不能仅靠 MCP 停权强制收回；受管脚本与 Agent 可执行登记的退出流程，但不能声称管控了任意本地副本。

发布清单无法核验时，当前客户端暂停受管项目调用，符合先检查后工作的策略；因此更新入口可用性也是开发可用性的依赖。后续收尾工具必须能在明确的协议范围内处理失败恢复，不能因为常规版本门禁而永远无法保全工作。

## 4. 项目组模型的后续调整

以下为实现建议，需要配套迁移、接口、RLS 和审批校验，不应只改界面名词。

1. 保留现有 `projects.id` 作为顶层协作空间 ID，逐步补 `subprojects`。管理员仍只管理分配给自己的协作空间。
2. 增加独立仓库 ID 和子项目路径映射，按本人授权拉取独立工程仓库并组装项目组；共享文档和业务日志另行明确来源和访问范围。
3. 仓库和子项目接入遵守“项目只能由超管创建”的限制，不能借注册资源绕过超管批准。增加资源是否扩权，必须进入授权校验。
4. 组级入口提供共同架构、规范及子项目目录；成员只能获得其批准范围内的目录和正文。全平台清单仅供超管使用。
5. 上下文定位返回允许访问的子项目、仓库快照、角色和相关资料。已获准的跨子项目任务可以加载多个子项目，禁止把本地一个“专注项目”字段当成全组唯一工作状态。
6. 跨子项目需求用父任务和子任务表达依赖。认领归属于执行实例；路径预留包含仓库和子项目，防止两个任务改同一份共享代码。
7. 不同仓库各自保留 Git 提交。组级检查点关联一组提交及验证证据，明确哪些资料已同步、哪些尚未交付。
8. 部署清单记录组级共享产物和各子项目产物。卸载范围由撤销范围、清单和引用共同决定，移出一个子项目不能清掉仍有权限使用的共享框架。

## 5. 建议实施顺序与验收

| 顺序 | 交付 | 验收结果 |
|---|---|---|
| 1 | 组／子项目／仓库模型与授权范围 | 一个协作空间登记两个独立工程仓库，成员只拉获准资源；新增资源不能隐式扩权 |
| 2 | 原框架安装和上下文恢复 | 从一个已有项目组工作区部署，生成真实入口和归属清单；两个 harness 能恢复同一组的正确资料，专注状态互不干扰 |
| 3 | 多来源文档与 Git 更新 | 两个仓库同名文档可区分；引用包含各自提交；未授权资料不进入上下文；修改经 Git 同步后另一设备可读取 |
| 4 | 任务认领与跨子项目交接 | 架构师拆分跨工程任务，两个执行实例竞争只有一个成功；旧代次不能提交；交接包含可恢复工作 |
| 5 | 框架升级及撤权收尾 | 对话开始区分并检查客户端／框架版本；保留人工文档修改；撤权后工作保全、回执和完整清理可重试 |
| 6 | 真实双设备及客户端矩阵 | 按 Windows/macOS 和七种 harness 逐项验收；完成备份恢复 |

真实试点可以包含用户提供的 `kms`，但其私有凭证、子项目构成、仓库分支和实际路径尚未核验。不能从仓库名字推断项目组结构。
