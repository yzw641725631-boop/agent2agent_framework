# 持久代码交接与恢复验收

日期：2026-11-09。发布版本为服务端 0.7.0 / 迁移 0010、Windows 0.9.0；实际发布状态见文末。本批继续完善多人开发的代码交接和运维，不代表完整七点生产目标已经达成。

## 这次解决什么

原先共享日志只保存文字、文件哈希及 Git 提交引用。原设备损坏或原作者离开时，其他人不能仅凭这些信息恢复未提交代码。本批增加独立的持久代码备份；日志共享、代码备份、Git 交付各有自己的不可覆盖回执。

用户流程：**每轮保存工作日志 → 核对代码备份状态 → 接手人读取获准日志 → PC 取回检查点 → 导出到新目录 → 审查后按 Git 流程接续。** 详细操作见[使用指南](../使用指南.md)。

## 实现与限制

| 能力 | 当前实现 | 明确边界 |
| --- | --- | --- |
| 自包含工作树 | Git 基线 commit 正文及全部普通文件，加实际新增、修改与删除清单；复核 blob/tree/commit 及 SHA-256 | 不含完整 Git 历史、Git 索引状态、忽略文件、依赖缓存与个人凭证；不自动处理 LFS/submodule |
| 安全传输与存储 | 当前设备 DPoP 身份、HTTPS、独立二进制入口；服务端 AES-GCM 加密卷，数据库保存归属和回执 | 备份不是本机可信执行证明；无法证明执行者没有在平台外另存或修改代码 |
| 授权继承 | 项目、仓库代码读取、日志可见性共同约束恢复；上传限定原作者设备 | 超管拥有平台范围权限；只有资料权限不能下载业务代码 |
| 补传 | 日志与代码分别持久待发，程序重试；PC 可显式重试 | 仍获授权的作者设备可补传已登记日志，即使租约结束；撤权后不能靠原会话补传 |
| 代码恢复 | MCP 下载到本机系统加密检查点；PC 导出 `working-tree/` 和说明到新目录 | 不覆盖业务目录、不执行代码、不自动认领任务，也不恢复原 HEAD 的完整历史 |
| 提交门禁 | 新建且绑定仓库的 observed 任务，最新日志必须有对应可解密快照才能提交 | 旧 legacy/declaration 模式仍兼容，不属于相同代码保证范围 |
| Git 交付 | 推送后服务器用上游凭证查询确切任务分支；登记独立 `code_deliveries` | 不等于 PR、合并、CI 测试或部署；网络查询后重新检查身份、租约、最新日志与仓库版本 |
| 存储巡检 | owner 运维 CLI 校验所有归档的解密与摘要，报告缺失、损坏、孤儿、剩余容量 | 不修改成功回执；只在显式选项下隔离超过 24 小时的未登记文件，不自动删除已登记代码 |

基线限 1000 文件、16 MiB，变更限 100 文件、16 MiB，单文件 4 MiB；gzip 上限 36 MiB，解压 JSON 上限 48 MiB。本机合计 512 MiB，默认服务端每项目 1 GiB、全站 16 GiB。超限或存储故障时保留工作，不伪造成功回执。链接、路径逃逸、跨平台大小写冲突、保留名称、凭证路径和已识别私钥/Token 内容被拒绝；内容检查不等于通用秘密识别。

回执的 `disaster_redundant: false` 保留：服务器接收成功并不能证明该条记录已进入另一台机器的最新备份。

## Token 与长期记忆

代码归档由程序通过二进制 HTTP 上传和取回，不把源码或压缩包编码送进模型正文。写日志返回精简日志回执，避免再复制整段说明和完整变更清单；最近日志索引、按需原文和程序心跳继续沿用。新增工具描述和回执仍消耗上下文，不能将上述措施换算成未经计量的节省比例。

本批没有安装 pgvector，也没有将共享日志自动提炼成长期记忆。后续仍须完成原文来源、增量水位、有效/过期状态、冲突处理、权限变化后的派生清理、检索预算及开工准备包加载。仅存向量不能完成这些要求。

## 运维方案

代码卷：`/opt/agent-hub/artifacts/work`，应用 uid 10001、目录 0700；不保存在容器可写层或本机数据库。上传落盘先 fsync、独占发布，再提交数据库回执；提交失败可能留下孤儿文件，因此巡检必须区分未登记文件与已接收归档。

`backup-server.sh` 使用固定摘要的 restic 0.19.1 镜像，将 PostgreSQL custom dump、角色定义、不可覆盖制品、服务与数据库配置一起加密备份，完成后全仓库读数据校验。数据库先建立一致快照，制品再读取；因为制品先落盘再登记且不覆盖、不自动删除，后续复制保留数据库引用的文件。HUB_SECRET 不在备份期间轮换，轮换需单独迁移现存密文。

这种安排依据 [PostgreSQL SQL dump 的一致性保证](https://www.postgresql.org/docs/current/backup-dump.html)、[Docker 持久化存储说明](https://docs.docker.com/engine/storage/volumes/)及 [restic 仓库与密码管理](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html)。代码备份密钥来自 HUB_SECRET 的独立域派生；restic 使用另一份独立密码。密钥与数据库/制品缺一，不能恢复。

提供每日备份、每日制品巡检、每月恢复演练及每五分钟运维检查的 systemd service/timer。恢复演练固定使用最近完整成功备份的确切快照 ID，只创建 `hub_restore_时间戳` 临时数据库，使用恢复出的密钥解密恢复出的全部制品；检查通过才清理该次恢复副本。失败保留证据，不覆盖正式业务库。恢复时明确恢复 uid 10001 的制品目录归属，不能把 root 的临时复制属主直接用于应用。

服务器 restic 仓库不是长期异地容灾。已完成一次加密异地复制和独立密码保管，持续异地备份目标、监控外部告警和容量保留策略仍需配置；每五分钟检查备份/恢复时效、失败任务、磁盘及签名更新清单并留下状态文件，不能声称已向管理员可靠送达告警。操作见[运维说明](25_备份巡检与恢复操作.md)。

## 已完成验收

- 腾讯云服务器独立 `hub_test`：**121 项**通过。上传、幂等、加密、不可覆盖、配额、损坏拒绝、提交门禁、仓库隔离、作者撤权后接手，以及 GitHub 核验期间撤权均覆盖。既有 TestClient/httpx 弃用提示仍存在。
- Windows 桌面：**91 项**通过。包含真实 Git 的基线、本机提交与未提交修改、二进制、删除、新目录导出，独立补传状态、账号切换、摘要验证和下载中断。
- **真实 Windows Controller → HTTP/DPoP → 实际 ASGI → PostgreSQL → 加密卷**：作者上传后被撤权，另一个获准身份取回完整工作树；其他仓库身份被拒绝。恢复包含未变化中文设计文件、新增二进制、未提交修改和删除，原工作目录保留。两个设备身份在一台 Windows 主机，不计作两台物理设备验收。
- **实际 restic 加密备份 → 新目录恢复 → 新 PostgreSQL 数据库 → 制品解密**：恢复 1 个非空代码快照及作者撤权状态，通过全仓库数据校验。没有用 `pg_restore --list` 代替实际恢复。
- **真实 Electron、Controller 与系统加密存储**：展开日志显示备份，点击取回、检查本机独立备份状态、导出完整源码及保留现有目录均通过；元数据 API 隔离，真实服务授权由上述网络与 PostgreSQL 验收覆盖。
- Ruff E/F/I/UP/B（排除 E501）、Skill 校验和实际 Nginx 配置校验均通过。
- 运维监控 **12 项**在服务器容器通过：备份缺失/过期/不完整、时间异常、链接、任务失败、低磁盘、更新签名失败与临近过期均有明确状态，异常正文不进入公开报告。Windows 同组测试 11 项通过、链接测试受系统权限限制跳过；服务器已实际覆盖。

## 对完整生产目标的复评

| 目标 | 当前结论 | 剩余必要工作 |

| 多项目组、独立仓库与逐人授权 | 可进入受限试点 | 真实私有业务仓库与多人授权验收；组内依赖与集成约束 |
| 人与多设备 Agent 同时协作 | 有任务租约、执行身份、日志和恢复 | 跨任务同文件冲突、独立 worktree、任务依赖、可靠消息与角色调度 |
| 原 install 规章与专注模式 | 有版本规则、路径检查、提交约束 | 全量规章迁移与验收、宿主写入前拦截或执行隔离；MCP 不能阻止宿主绕过工具写文件 |
| 每轮记录与可见进度 | 显式日志实时共享，PC/Web 可见 | 宿主轮次结束/中断钩子、漏记检测、真实提交对应的 CI 证据 |
| 共享、提炼、自净的长期记忆 | 未实现 | pgvector、混合检索、来源与增量提炼、过期/冲突/撤权清理、按预算自动加载 |
| 统一安装、升级与跨端职业拆分 | Windows 首批三宿主有基础 | macOS、其他四工具的实际验收；安装归属与角色执行边界；Windows 代码签名 |
| 撤权交接、卸载与生产运维 | 已有正常授权下的持久交接与恢复 | 专用撤权收尾身份、失败保全和按部署清单卸载；持续异地备份、外部告警、保留策略及受支持系统迁移 |

**本批补齐了可验证的正常代码交接链路。完整平台仍不能按七点全部生产可用验收。** 下一主线应先完成专用撤权收尾和安装归属，再实施共享记忆治理；原作者尚未上传的工作不能仅靠服务器回执找回。
