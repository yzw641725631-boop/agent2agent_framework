# 服务器并发、容量与故障演练

2026-11-11｜对应原计划阶段E的有界并发与进程故障验收。服务端 **0.22.0 / schema 0032**，Windows保持 **0.23.1**。本轮只新增演练入口和证据，没有修改产品运行代码、迁移或正式发行包。

## 执行环境

全部Docker、PostgreSQL及数据库测试在服务器47执行。使用新建的内部网络、数据库容器和专用数据卷；数据库名为`hub_test`，随机生成数据库密码和应用密钥，不复用正式凭证。测试容器不加入正式数据库网络，不映射宿主机或公网端口。

| 进程 | 内存上限 | CPU上限 |
| --- | ---: | ---: |
| 普通API，单Uvicorn进程 | 512 MiB | 0.75 |
| PostgreSQL 18.6 / pgvector | 384 MiB | 0.50 |
| HTTP驱动 | 192 MiB | 0.25 |

全部禁用swap。初始化进程退出后才启动API和驱动。被测API使用普通`create_app`、`hub_runtime`及原有连接池、DPoP、RLS、事务锁与限流；没有添加测试HTTP路由或替换业务方法。合成账号在单独的初始化进程通过现有接口建立，测试会话有效期设为1800秒。

最终驱动耗时 **42.030秒**，包含负载、锁等待、两次进程故障及恢复核验，不包含建库、迁移、初始化与清理。最终源码摘要、全部分档结果、进程ID、资源采样和收尾检查见[验收数据](审计数据/2026-11-11_服务器并发容量与故障演练.json)。

## 八项检查通过

| 检查 | 实际结果 |
| --- | --- |
| 16路竞争认领 | 两个合成成员的不同实例争抢同一任务，1个成功、15个`TASK_ALREADY_CLAIMED`，数据库恰有1个活动运行 |
| 16路同操作认领 | 相同幂等键、相同实例返回相同结果，数据库恰有1个活动运行 |
| 16路同操作日志 | 返回同一日志及回执，数据库仅1条对应记录 |
| 并发二进制备份 | 4路上传、两个项目各重复一次；每份包含2 MiB随机变更，最终2个快照。下载字节摘要与原包一致，重复上传复用回执，另一项目成员下载返回404 |
| 混合负载及隔离 | 五档共800次请求，640次200、160次预期404，没有429、503或意外错误；160次成功写入与数据库数量完全一致 |
| 真实锁等待与繁忙恢复 | 独立数据库事务持有恢复屏障锁，32路请求全部返回`503 SERVICE_BUSY`及`Retry-After: 3`；释放锁后连续5次业务读取成功 |
| API强制终止 | 已提交日志和备份后，SIGKILL终止整个测试API进程；停机请求出现真实连接失败，新进程复用原日志与备份回执，中断期间的操作重试后只有1条记录 |
| 数据库强制终止 | SIGKILL终止测试PostgreSQL主进程；API写请求返回503，新数据库进程出现实际WAL崩溃恢复记录。API进程保持原PID，连接池恢复后复用原记录，两份备份字节及回执保持一致 |

锁等待的32路失败批次耗时 **6.380秒**，释放后5次业务读取共 **0.165秒**。恢复时间的完整定义及实测值以JSON中`faults`为准：`authenticated_retry_after_restart_seconds`从驱动收到“已启动”信号计时，数据库信号在`pg_isready`成功后发出；这组数值不构成业务RTO承诺。

最终数据库共 **167条日志、2个快照**：2条初始代码日志、1条并发幂等日志、160条混合负载日志，以及两次故障各2条唯一日志。快照同时核对元数据回执、加密存储后的实际下载包和跨项目拒绝结果。

## 分档测量

每档160次请求，比例为：任务详情20%、日志列表20%、新增日志20%、跨项目任务读取20%、本项目仓库列表20%。每次请求生成新的DPoP证明。常规负载没有自动重试，成功写入逐档与数据库数量核对。

| 并发数 | 请求/秒 | P50毫秒 | P95毫秒 | 成功写入 | 预期404 | 意外错误 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 45.60 | 20.51 | 31.93 | 32 | 32 | 0 |
| 4 | 37.40 | 104.90 | 155.08 | 32 | 32 | 0 |
| 8 | 35.73 | 226.10 | 304.83 | 32 | 32 | 0 |
| 16 | 33.67 | 465.24 | 653.52 | 32 | 32 | 0 |
| 32 | 33.15 | 868.45 | 1313.94 | 32 | 32 | 0 |

这是共享服务器、CPU限额及单个受限驱动下的合成短时观测，延迟统计包含预期拒绝请求。并发提高后排队明显，当前结果适合记录这组工作负载的基线；没有测得最大可持续容量，也不据此承诺生产吞吐量。

约10秒一次的资源采样中，API、数据库和驱动的最大观测内存分别为113.7、132.2、118.0 MiB；采样值不是精确峰值。没有容器OOM。执行期间8次正式健康探测全部成功，最慢0.200秒；前后正式API与数据库的容器身份、启动时间、正式镜像、发行目录、0032结构及生产卷保持一致。

## 复现入口

- [run-server-resilience.py](../projects/agent-hub/scripts/run-server-resilience.py)：仅Linux服务器运行的宿主编排器。生成一次性凭证，创建带随机运行标签的测试资源，注入SIGKILL，核验归属后清理专用容器、网络、卷和合成身份。
- [server_resilience_fixture.py](../projects/agent-hub/tests/server_resilience_fixture.py)：分别以`seed`、`serve`、`drive`运行。初始化与HTTP负载分离，API重启不重新初始化数据库，驱动通过私有目录与编排器同步。

在服务器的独立源码目录准备当前受控源码、已缓存的测试运行镜像及PostgreSQL镜像，并在源码根目录准备已校验的`cl100k_base.tiktoken`。下载入口为`python3 scripts/cache-memory-tokenizer.py cl100k_base.tiktoken`，实际演练容器只使用本地文件。当前编排器核验本服务器的正式服务及旧测试库状态，不能直接当作任意主机的通用压测工具。

本轮实际使用的镜像ID保存在JSON的`images`中。运行示例，报告路径必须尚不存在：

```bash
python3 scripts/run-server-resilience.py --allow-disposable-server-test \
  --postgres-image "$RESILIENCE_POSTGRES_IMAGE_ID" \
  --runtime-image "$RESILIENCE_RUNTIME_IMAGE_ID" \
  --report /opt/agent-hub/application/candidates/resilience-new-report.json
```

这两个变量应填写服务器已存在的完整`sha256:`镜像ID。环境凭证由编排器在权限0600的临时文件中生成，不放入命令参数或报告。至少要求1400 MiB可用内存及2 GiB磁盘，源码不能位于正式发行目录。HTTP驱动与API均不挂载Docker套接字。

首次准备因演练代码重复传入`scope`而退出，未进入负载阶段，资源均已清理。修复后完整通过；随后整理脚本、固定闭包参数及补记正式API进程身份，重新执行最终源码得到本页结果。没有把首次准备失败记录为产品故障，也未用早期数据替代最终源码证据。

## 收尾与剩余范围

独立收尾检查确认：本轮标签下的容器、数据卷和网络全部移除，随机环境文件与合成设备私钥目录均已清理；原测试数据库继续保持停止。正式卷`agent-hub-postgres-data`保留，正式API及数据库没有重启。本轮不需要发布新版本。

本轮覆盖已建立会话的短时HTTP负载、2 MiB二进制快照并发、真实数据库锁等待及提交后的进程崩溃。长期浸泡、登录密码吞吐、SSE连接规模、全尺寸快照并发、记忆检索及模型负载、磁盘写入中途断电、文件系统损坏和异地恢复仍待专项执行。此前[大仓库门禁](40_大仓库交接与长期记忆基准.md)独立覆盖单次64 MiB基线和16 MiB变更，不能据此推导并发上限。

阶段E已补充这组容量与故障证据；外部告警、异地副本与恢复、长期业务规模等生产资格仍有缺口。两台物理设备尚未提供；真实业务试点和macOS继续暂缓。当前工程只有安装MCP连接，本轮文档与证据保存在仓库，没有固定项目工作日志的共享回执。
