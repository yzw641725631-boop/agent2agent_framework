# 撤权收尾与归属卸载

日期：2026-11-09。实现版本：服务端 **0.8.0 / Alembic 0011**、Windows **0.10.1**。发布与验收状态见文末。

## 用户流程

**撤权立即停止普通权限 → 释放原任务租约 → 原设备限定上传工作 → 服务器逐条确认可恢复代码 → 核对收尾清单 → 卸载按项目登记的框架 → PC/Web 查看结果。**

管理员可在 Web“撤权交接”查看上传状态和设备清理报告、由超管延长过期收尾窗口。被撤权设备不需要重新登录普通会话；桌面利用已登记的原设备密钥访问上传专用通道。项目 MCP 必须要求 Agent 停止开发并调用 `hub_run_closeout`；后台每 30 秒恢复待办，普通调用、进度通道发现权限变化时会立即安排检查。

## 服务端边界

- `closeout_jobs` 保存撤权原因、原身份代次、授权 ID、仓库版本及有效期；`closeout_runs` 冻结原作者、设备、项目、仓库、任务、运行和已确认规则。已确认的旧上下文也可交接，不要求租约继续有效。
- 专用凭证绑定原设备 P-256 DPoP，域与普通登录隔离；可发现本人设备的收尾任务、追加工作日志、上传原任务快照、取得收尾确认、回报清理。没有普通登录、资料读取、任务认领、Git 推送、评审或部署权限。凭证仅在加密桌面状态中保存，不返回模型。
- 仅在成员移除、非 active 账号状态、设备撤销、仓库读/写权限缩减、仓库归档时创建任务。普通续期、扩权、网络异常、会话过期和主动退出不创建卸载任务。重新授权的 grant/设备代次、重新启用仓库的版本与旧安装区分；不依据客户端时钟决定删除范围。
- 使用单独 RLS 策略，仅允许原运行的收尾日志与对应快照；普通任务、文档和他人日志仍不可见。管理与收尾都沿用身份/资源/项目协调锁；上传网络等待不持有数据库事务。
- 每个客户端 operation_id 对应固定日志 ID；重试不能更换内容。代码沿用自包含 Git 工作树格式、AES-GCM 加密卷、摘要、容量与秘密路径检查。源码走二进制 HTTP，不经过模型正文。
- 收尾确认需要清单与该任务全部已登记日志一致、每条存在且能解密的代码快照。新日志会撤销旧确认；服务器保留不可覆盖的历史收尾回执。存在原执行记录时，空清单不能授权卸载。
- 默认收尾窗口 30 天，超管可延长 1–30 天。过期后不接受新代码，保留已有工作与证据；已上传后的设备结果仍可回报。清理结果明确是 `client_report_only`，不是设备可信执行或擦除证明。

## 桌面保全与卸载

在停止对应运行并等待已准入操作结束后，读取加密待发记录、对最新受管运行采集最终工作树；保留人工日志，新增自动日志不声称测试通过。上传、确认后再次检查业务文件是否变化；编辑器仍在写、快照超限、损坏、未知工作或网络错误时停止清理。

安装器按项目持有三宿主 MCP 收据，以及 `.agent-hub/framework/<连接名>/` 内框架文件的逐文件摘要清单；`deployFramework` 可登记规则、脚本和测试。同一工程的不同项目/连接使用独立目录和收据，不能共享文件归属。卸载只删除目录范围内内容未变化的已登记文件，精确移除本项目 MCP 项，移除本地项目连接描述符，最后只清理空目录。没有递归删除工程。

保留业务代码、Git、用户自改文件、未知文件、加密工作检查点和安装前备份。其他项目的连接、共享桌面端和通用 Skill 保留。断开连接的新版安装也保留归属墓碑以便撤权后收尾。全部安装收据均缺失的旧手工框架不能安全推断，不能宣称已将其完整卸载。

上传成功、卸载冲突和结果待回报分别持久记录。上传回应丢失可按固定 ID 重试；清理结果回报失败只重发结果。MCP 对已撤权连接只列出收尾工具，PC 未登录普通会话也能查看“撤权交接”；Web 管理员每五秒刷新最近记录。

## 仍未完成的总体目标

本批推进撤权交接，不代表整个框架生产目标全部完成。共享记忆的增量提炼、冲突/过期治理、pgvector/混合检索与按预算自动加载仍待实施；跨端独立角色调度、完整 install 角色迁移、每轮宿主钩子、macOS/其余工具、两台物理设备验收也仍缺。持续异地备份、外部告警和受支持服务器系统迁移沿用既有待办。

MCP 无法阻止宿主绕过工具修改文件，客户端也不能证明历史副本已从机器上擦除。停止桌面进程、设备私钥丢失或长期完全离线时，服务器无法主动取得该设备尚未上传的数据；恢复连接及密钥前不能完成自动交接。

### 本轮复核后的修正

同目录的不同项目/连接现在各有框架子目录与收据；卸载一个连接不会删去另一个连接的同名脚本。已完成收尾不会在下一次发现任务时被重新显示为未卸载。断开的绑定保留归属墓碑；重新授权的身份代次和仓库版本不会由旧任务卸载。恢复演练使用本次 0.8.0 镜像，保持与当前迁移一致。

0.10.0 发布后的复核发现待发队列原为倒序，较早人工日志可能在最终快照之后登记，导致接手人默认看到旧快照。本轮追加 0.10.1，将旧日志先上传、最终观察检查点最后登记；单元回归和真实 PostgreSQL 联调均验证默认最新日志对应最终代码。0.10.0 的工作没有丢失，但应升级至修复版；既有日志时间不重写，历史交接须按收尾清单核对最终观察检查点。

### Token 基线

[0.10.1 测量](审计数据/2026-11-09_0101_Token测量.json)使用 `o200k_base`：Skill 正文 **1,807**、仓库开发工具定义 **3,734**（28 项）、完整仓库管理工具定义 **4,614**（31 项）。撤权连接只保留版本检查和两个收尾工具，共 **297**（3 项）；按需撤权参考文档另计 **532**。

这些数字仅测公开文本和工具定义，不包括宿主封装、对话历史、推理、工具输出与缓存计费，不是账单或生产节省比例。新增两个收尾工具使完整开发工具上下文比 0.9.0 增加约 201 Token；长期历史的检索预算和自动提炼仍须下一阶段实现。

### 接下来的实施顺序

下一主线是共享记忆：保留日志原文和证据，先建立来源、增量水位、有效/过期/冲突状态及仓库权限继承，再接入服务器 PostgreSQL 的 pgvector/混合检索，最后通过开工准备包按 Token 预算自动加载。后台定期提炼不能每次重复扫描全部历史，派生记忆也不能扩大原文权限。随后完善完整角色文档部署、逐轮宿主钩子和跨端独立评审调度。

**本次完成并验证了受管撤权交接这一批能力；完整平台的七项目标仍未全部生产验收。**
